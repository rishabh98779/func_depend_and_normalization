1. Relational Model Foundations and the Idea of a Key

Part 1  •  the vocabulary you must not get wrong

Every later topic in these notes — dependency, normalization, join, view — is built on one small piece of vocabulary. Learn it precisely here and the rest of the book reads easily. The source opens the key chapter with a note that is worth taking seriously: “The terms ‘relation’ and ‘table’ are used interchangeably; the terms ‘tuple’ and ‘record’ are used interchangeably. So, don't get confused!”

1.1 Relation, Tuple, Attribute and Domain

A relation is a table of values arranged in rows and columns, where the order of the rows and the order of the columns do not carry meaning. Each row is a tuple (a record). Each column is an attribute (a field), and each attribute draws its values from a permitted set called its domain.

Definition

A relation is a set of tuples over a fixed set of attributes. A tuple is one row. An attribute is one column name. The degree of a relation is its number of attributes; its cardinality is its number of tuples.

1.2 Why a Database Needs Keys

The source gives three reasons, and they are the right three. A real table may hold thousands of rows, and some of those rows may look identical in every column a user cares about. A key is what makes a row addressable anyway.

Why keys exist (source reasons)

1. Unique identification. Keys let you identify any row of data in a table even when records appear duplicated in ordinary columns.

2. Relationship building. Keys allow you to establish and identify the relation between two tables.

3. Identity and integrity. Keys help you enforce identity and integrity in those relationships.

1.3 The Vocabulary Trap: Relation = Table, Tuple = Record

Because the source's slides mix the formal and informal words in the same paragraph, the following table is worth keeping beside you while reading Part 1.

Writing “relation” to mean “relationship”. In the relational model a relation is a table. The link between two tables is a relationship, and it is implemented by a foreign key. Mixing the two words in an answer costs marks in viva.

2.1 Super Key

Definition

A super key is a set of attributes that can identify each tuple uniquely in the given relation. A super key is not restricted to any particular number of attributes — it may consist of any number of attributes, and it may carry extra attributes that are not needed for unique identification.

The source's own caution is the key sentence: all the attributes in a super key are sufficient to identify each tuple uniquely, but all of them may not be necessary. A super key may therefore contain a smaller set that would already have done the job.

Example 1 — the Student schema

Given Student ( roll, name, sex, age, address, class, section ), each of the following sets is a super key, because each set uniquely identifies every student:

  • ( roll, name, sex, age, address, class, section ) — the whole tuple
  • ( class, section, roll ) — a minimal one
  • ( class, section, roll, sex ) — minimal set plus an extra attribute
  • ( name, address ) — unique in this schema

Example 2 — the Employee schema

In the source's Employee example, Emp_SSN and Emp_Num are each super keys.

Common mistake

Assuming that every combination of columns is a super key. Only sets that actually guarantee uniqueness qualify. In the Student schema, ( class, section ) alone is not a super key, because many students share a class and section.

2.2 Candidate Key

Definition

A candidate key is a minimal super key — a set of the fewest possible attributes that can identify each tuple uniquely. Equivalently: a super key from which no attribute can be removed without destroying uniqueness.

From the same Student schema, the candidate keys are ( class, section, roll ) and ( name, address ). The set ( class, section, roll, sex ) is a super key but not a candidate key, because sex can be removed and the set still identifies a student.

Properties of a candidate key (from the source)

PropertyConsequence
Must contain unique valuesNo two tuples share a candidate-key value
May have multiple attributesIt can be composite
Must not contain NULLA NULL would be “unknown”, so it cannot identify
Should contain the minimum fields neededMinimality is what separates it from a super key
Uniquely identifies each recordThat is its whole purpose
Explanation — why minimality matters

Minimality is not fussiness. A candidate key is the smallest piece of information you must supply to pin down exactly one row. If you store a larger set as “the” key, you force users to supply redundant data and you allow inconsistencies: the extra columns could be changed to contradict the identifying ones.

Example 2 — a table with three candidate keys

In the source's student table, Stud_ID, Roll_No and Email are all candidate keys; each one independently identifies a student record.

Facts to memorise

Every table has at least one candidate key. A table may have several candidate keys but only one primary key. Every attribute that appears in some candidate key is called a prime attribute; all other attributes are non-prime. This prime/non-prime split is the language of 2NF and 3NF in Part 3.

2.3 Primary Key

Definition

A primary key is the candidate key that the database designer selects and implements. It is the official identifier of the relation.

Rules for defining a primary key (from the source)

  1. Two rows cannot have the same primary-key value — it must be unique.
  2. Every row must have a primary-key value — it cannot be NULL.
  3. The value in a primary-key column can never be modified or updated while any foreign key refers to it.
  4. A relation is allowed to have only one primary key.
Common mistake

“A table can have two primary keys.” No. A table can have several candidate keys; exactly one of them becomes the primary key, and the rest become alternate keys. Two separate primary keys would give two conflicting notions of identity.

2.4 Alternate Key

Definition

An alternate key is a candidate key that is left unimplemented after the primary key has been chosen. All the candidate keys that are not the primary key are alternate keys.

In the source's example, Stud_ID, Roll_No and Email are all qualified to be primary key. Because Stud_ID is chosen, Roll_No and Email become the alternate keys.

2.5 Foreign Key and Referential Integrity

Definition

An attribute X is a foreign key referring to attribute Y when the values of X must come from the values that actually exist in Y. The relation containing Y is the referenced relation (also called the master or primary table); the relation containing X is the referencing relation (also called the foreign table). X may have a name different from Y.

The source's example uses two relations:

Employee ( Emp_ID, Emp_Name, …, Dept_ID )Department ( Dept_ID, Dept_Name )
t_dept takes only values present in dept_no of DepartmentDept_ID is the primary key here

Notes on the foreign key (from the source)

  • A foreign key references the primary key of the referenced table.
  • It can take only those values that are present in the primary key of the referenced relation.
  • It may have a name different from that of the primary key it references.
  • It can take the NULL value (meaning “no department assigned yet”).
  • There is no restriction that a foreign key be unique — in fact it is usually not unique.

2.6 Partial Key

Definition

A partial key is a key that cannot identify all the records of a table uniquely. It can, however, select a bunch of related tuples from the table.

The source's example makes this concrete:

Table 2.3 — Department ( Emp_no, Dependent_name, Relation ).
Emp_noDependent_nameRelation

Using Emp_no alone we cannot identify a single tuple — E1 appears twice — but we can select the group of tuples belonging to E1. Emp_no is therefore a partial key. In entity–relationship modelling this is exactly the “partial key” of a weak entity; the full identifier is the partial key together with the owner's key.

2.7 Composite Key and Compound Key

Definition

A composite key is a primary key made up of two or more attributes rather than a single attribute. The combination guarantees uniqueness even though each individual column may repeat values.

Table 2.4 — A composite key in action. Neither column is unique alone; the pair is.
Student_NameCourse_Code
RahulCS101
PriyaCS101
RahulMA201
SanaCS101

Student_Name repeats (“Rahul” twice) and Course_Code repeats (“CS101” three times), but the pair ( Student_Name, Course_Code ) is unique, because a student cannot enrol in the same course twice. That pair is the composite primary key.

Composite versus compound — as the source draws the line

The source states the difference explicitly: any part of a compound key can be a foreign key, but the composite key may or may not be part of a foreign key. In other words, a compound key is a composite key in which each component is itself a foreign key to a different table. A many-to-many junction table such as Enrolment ( Student_ID, Course_ID ) has a compound key, because both components are foreign keys.

From the source — an inconsistency handled honestly

The source's summary list defines Composite Key with the wording “An artificial key which aims to uniquely identify each record is called a surrogate key…” — that is the surrogate key definition pasted under the wrong heading, because the two sentences below it define “Surrogate Key” with the same words. Later in the same chapter, “Composite Key” is correctly defined as a primary key of multiple attributes. These notes follow the later, correct definition and treat the earlier line as a copy error in the source. Nothing else in the chapter depends on it.

2.8 Unique Key

Definition

A unique key is unique for all records of the table, is non-updatable once assigned, and may contain a NULL value.

The source's example is the Aadhaar card number, and it is a good one because it exercises all three properties at once:

  • It is unique for all citizens (tuples) of India (the table).
  • If the card is lost and a duplicate copy is issued, the duplicate always carries the same number — so the value is non-updatable.
  • Some citizens have no Aadhaar card yet, so for those rows the value is NULL.
Explanation — unique key versus primary key

The single practical difference is the NULL rule. A primary key forbids NULL and permits exactly one per table. A unique key permits NULL and a table may declare several of them. Both enforce uniqueness on the values that are present.

2.9 Surrogate Key

Definition

A surrogate key is an artificial key created to identify each record uniquely. It is unique because it is generated when no natural primary key exists. It lends no meaning to the data, is usually an integer, and is generated just before the record is inserted.

The source's example is the mobile number of students in a class where every student owns a mobile phone. The source also lists the two situations in which surrogate keys are allowed:

  • When no existing property has the characteristics required of a primary key.
  • When the natural primary key is too big or too complicated.
Common mistake

Confusing a surrogate key with a unique key. A surrogate key is artificial and updatable; a unique key is typically a natural, non-updatable attribute (Aadhaar number, passport number). The source's own definitions of the two make this distinction by listing “updatable / not updatable” as the separating property.

2.10 Secondary Key

Definition

A secondary key is a key required for indexing, so that searching is better and faster.

Unlike the previous nine keys, a secondary key says nothing about uniqueness. It is a performance device: it is the attribute you commonly search on, and an index is built over it so the DBMS can avoid a full table scan. In the Student schema, if the query “find all students of class CSE-3A” is common, class would be a secondary key.

3. Functional Dependencies: Meaning and Notation

Part 2  •  the single idea that makes normalization possible

Normalization is not a set of arbitrary rules. It is a set of tests applied to functional dependencies. If you cannot see the dependencies hiding in a table, you cannot normalize it — you can only memorise the steps. This chapter builds the ability to see them.

3.1 What a Functional Dependency Says

Definition

A functional dependency (FD) is a constraint between two sets of attributes of a relation. If X and Y are sets of attributes of relation R, then X → Y (“X determines Y”, or “Y is functionally dependent on X”) means that any two tuples that agree on X must also agree on Y.

Formally, as the source states it: for any two tuples t1 and t2 in R, if t1[X] = t2[X] then t1[Y] = t2[Y].

Read that sentence slowly, because it is the whole subject. The arrow does not mean “causes”, it does not mean “is calculated from”, and it does not mean “appears to the left”. It means: in every legal state of this relation, the same X value cannot be paired with two different Y values.

The source's own example is the smallest possible one. Consider a Department relation with attributes DeptId and DeptName, where DeptId is the primary key:

Table 3.1 — The source's Department relation.

Because DeptId uniquely identifies the department, it also uniquely determines the department name. The dependency is

DeptId → DeptName

The source phrases the justification memorably: if you want to know the department name, then at first you need to have the DeptId. That “you must know X first” test is a reliable practical way to spot a dependency in a table.

From the source — a wording slip

The source then writes “DeptId is functionally dependent on DeptName” and still labels the dependency DeptId → DeptName. The sentence is backwards: in DeptId → DeptName it is DeptName that is functionally dependent on DeptId, not the other way round. The notation in the source is correct and is the one used throughout these notes; only that one explanatory sentence is inverted.

3.5 Trivial, Non-Trivial and Completely Non-Trivial

The source gives three forms of functional dependency. The distinction looks pedantic until you write an exam answer about BCNF, where the words “trivial” and “non-trivial” decide whether a dependency violates the form.

Definitions — the three forms

Trivial: for A → B, B is a subset of A. The dependency tells you nothing new.

Non-trivial: for A → B, B is not a subset of A.

Completely non-trivial: for A → B, A ∩ B is empty (the two sides share no attribute at all).

4. Armstrong's Axioms and Reasoning with Dependencies

Part 2  •  a small set of rules from which every valid dependency can be derived

A set F of functional dependencies that you write down for a schema is never the whole truth: it implies others. Armstrong's axioms are the inference rules that let you compute those implied dependencies. They were developed by William Armstrong in 1974, as the source notes.

4.1 The Three Primary Axioms

Armstrong's three axioms

Reflexivity. If Y is a subset of X, then X → Y. The source states it as “A → B, if B is a subset of A”. This is the rule that makes trivial dependencies true.

Augmentation. If X → Y, then XZ → YZ for any set of attributes Z. The source writes it as “AC → BC, if A → B”. Adding the same attributes to both sides preserves the dependency.

Transitivity. If X → Y and Y → Z, then X → Z. The source gives it as “If A → B and B → C, then A → C, i.e. a transitive relation”.

4.2 Derived Rules

Three further rules are commonly used because they shorten derivations. They are derived, not assumed: each can be proved from the three axioms.

Table 4.1 — Derived rules, all provable from reflexivity, augmentation and transitivity.
RuleStatementDerivation sketch
Union (additivity)If X → Y and X → Z, then X → YZAugment X → Y to X → XY; augment X → Z to XY → YZ; transitivity gives X → YZ.
Decomposition (projectivity)If X → YZ, then X → Y and X → ZY ⊆ YZ, so by reflexivity YZ → Y; transitivity with X → YZ gives X → Y.
PseudotransitivityIf X → Y and WY → Z, then WX → ZAugment X → Y to WX → WY; transitivity with WY → Z gives WX → Z.
Common mistake — decomposition is one-way

Decomposition works on the right side, never on the left. From A → BC you may conclude A → B and A → C. But from AB → C you may not conclude A → C or B → C. Splitting the left side is an invalid inference, and it is one of the most frequent mistakes in normalization answers.

4.3 Closure of a Set of Attributes

To decide whether a given set of attributes is a candidate key, you need to know everything it can determine. That is its closure.

Definition

The closure of a set of attributes X under a set of dependencies F, written X⁺, is the set of all attributes that can be functionally determined by X using the axioms. If X⁺ contains every attribute of the relation, then X is a super key; if X is also minimal, X is a candidate key.

Algorithm — computing X⁺

1. Start with the result set = X.
2. Scan the dependencies in F. If the left side of a dependency is already contained in the result set, add its right side to the result set.
3. Repeat step 2 until no new attribute is added.
4. The final result set is X⁺.

4.4 Worked Closure Computations

Worked step — a full closure

Relation R(A, B, C, D, E) with dependencies:

F = { A → B,  B → C,  CD → E }

Task: compute A⁺ and decide whether A is a candidate key.

PassResult setDependency usedReason

1{A, B}A → BLeft side {A} ⊆ result

Result: A⁺ = {A, B, C}. Since D and E are missing, A is not a super key and therefore not a candidate key.

Worked step — finding a candidate key by closure

Same relation R(A, B, C, D, E) with F = { A → B, B → C, CD → E }.

Task: test {A, D}.

PassResult setDependency used
start{A, D}—

Result: (AD)⁺ = {A, B, C, D, E} — every attribute. So {A, D} is a super key. Is it minimal? Test the proper subsets: A⁺ = {A, B, C} (missing D, E) and D⁺ = {D} (missing A, B, C, E). Neither subset determines everything, so {A, D} is a candidate key.

Correct result — the shortcut

Attributes that appear on the right side only can never be part of a candidate key. Attributes that appear on the left side (or nowhere) must be part of every candidate key. Here E appears only on the right, so E is excluded from keys; A and D appear on the left, so both must be present. Starting with {A, D} is therefore the right first guess — and the closure above confirms it.

4.5 Equivalence of Dependency Sets

Two dependency sets F and G are equivalent when every dependency in F is implied by G and every dependency in G is implied by F. Equivalence is what lets a designer replace a messy set of dependencies with a cleaner, smaller one without changing the meaning of the schema — and it is the theoretical justification for a lossless decomposition, covered in Chapter 12.

Explanation — why this is worth knowing

When you decompose a table in Part 3, the projections of the original dependencies onto the new tables form a new set G. If F and G are equivalent, the decomposition has preserved every constraint. If they are not, the decomposition has quietly lost a business rule — a fact worth stating in an exam answer.

5. Special Dependencies: Transitive, Multivalued and Join

Part 2  •  the three dependency types that drive 3NF, 4NF and 5NF

Ordinary functional dependencies are not the only constraint a table can violate. Three richer kinds of dependency each have a normal form aimed at them. Understanding them here makes Part 3 read as one connected argument rather than six unrelated definitions.

5.1 Transitive Dependency

Definition

A functional dependency is transitive when it is formed indirectly by two other dependencies. The source's precise statement: X → Z is transitive if all three of the following hold:

  • X → Y
  • Y does not → X  (so Y is not itself a determinant of X)
  • Y → Z

The source adds a useful scope note: a transitive dependency can only occur in a relation of three or more attributes, and it is the dependency that 3NF removes.

The source's Book example

Table 5.1 — The source's transitive-dependency example.
BookAuthorAuthor_age
Game of ThronesGeorge R. R. Martin66
Harry PotterJ. K. Rowling49
Dying of the LightGeorge R. R. Martin66

Check the three conditions:

  1. {Book} → {Author} — knowing the book tells you the author. ✔
  2. {Author} does not → {Book} — an author may write many books. ✔
  3. {Author} → {Author_age} — knowing the author tells you the age. ✔

Therefore, by transitivity, {Book} → {Author_age} holds: if you know the book name, you can know the author's age. That indirect dependency is a transitive dependency, and it is exactly the kind of dependency 3NF breaks.

Common mistake

Calling any two-dependency chain “transitive”. The middle condition matters. If Y → X also held, then X and Y would determine each other and the chain would simply be a pair of equivalent determinants, not a transitive dependency in the 3NF sense.

5.2 Multivalued Dependency

Definition

A multivalued dependency (MVD) occurs when the existence of one or more rows in a table implies the existence of one or more other rows in the same table. If a table has attributes P, Q and R, and Q and R are two independent multivalued facts about P, we write P →→ Q and P →→ R.

The source states the three conditions for a table to have a multivalued dependency, and they are worth listing exactly as given:

  1. For a dependency A → B, if for a single value of A multiple values of B exist, then the table may have a multivalued dependency.
  2. The table must have at least three columns for a multivalued dependency to exist.
  3. For a relation R(A, B, C), if there is a multivalued dependency between A and B, then B and C must be independent of each other.

Definition

A table is in join dependency if it can be recreated by joining multiple tables, each of which holds a subset of its attributes. A join dependency is a generalisation of a multivalued dependency, and it is the dependency that 5NF addresses: a relation is in 5NF only if it is already in 4NF and cannot be decomposed further without losing information.

6. Normalization Fundamentals and First Normal Form

Part 3  •  why we decompose at all

Before learning six normal forms, it helps to know exactly what disease they are treating. The disease is redundancy: the same fact stored in more than one place. Redundancy is not merely wasteful; it is the direct cause of three specific failures called anomalies. Normalization is the systematic removal of redundancy by decomposition, and each normal form removes one more kind of redundancy.

6.1 What Normalization Is

Definition (source)

Normalization is a process of designing a consistent database by minimising redundancy and ensuring data integrity through decomposition which is lossless. It is a systematic, step-by-step decomposition of complex records into simple records.

The source lists several characterisations, all of which are worth knowing because exam questions often ask for two or three of them.

  • It is a formal process of developing data structures.
  • It promotes data integrity.
  • It ensures data dependencies make sense — that is, data is logically stored.
  • It eliminates undesirable characteristics.

How normalization works, in the source's words

Normalization designs the schema by modifying the existing schema, reducing both redundancy and dependency of the data. Unwanted duplication is removed along with the anomalies. In an insert anomaly, values such as NULL are forced where they should not be; in an update anomaly, data cannot be updated correctly because the same value occurs multiple times in a column; in a delete anomaly, deleting one record removes facts that belong to other records. The aim is therefore to remove redundant data and store only related data in each table, which decreases database size and makes the data logically stored.

Update anomaly. If data items are scattered and not linked properly, updating one fact leaves copies elsewhere unchanged. Here “Ananya's department is CSE” appears twice; changing it in one row and not the other leaves the database inconsistent.

6.3 The Ladder of Normal Forms

The source lists six normal forms in order. Each is a stricter condition than the one before it, and each removes one more class of redundancy.

6.4 First Normal Form (1NF)

Definition

A relation is in First Normal Form if every attribute contains an atomic value. An attribute of a table cannot hold multiple values; it must hold only single-valued attributes. 1NF therefore disallows multi-valued attributes, composite attributes, and their combinations.

The source gives a second, equivalent statement that is worth remembering: 1NF is defined in the definition of relations themselves — all attributes in a relation must have atomic domains, and the values in an atomic domain are indivisible units. Each attribute must contain only a single value from its predefined domain.

Common mistake

Believing that 1NF is about the number of columns. It is not. 1NF is about the contents of one cell. A table with 200 columns is perfectly capable of being in 1NF, provided every cell holds exactly one indivisible value. Equally, a two-column table can violate 1NF if a cell contains a list.

Quick test for 1NF

Ask of every column: “Can this cell ever need to hold two values?” A comma-separated list, a set of tags, an array, or a repeating group in a cell all mean the answer is yes, and the relation is not in 1NF. The fix is always the same: move the repeated values into their own rows.

7. Second Normal Form (2NF)

Part 3  •  removing partial dependencies

2NF is the first form that depends on which attributes are prime. Before stating the rule, the source defines the two terms the rule needs.

7.1 Prime and Non-Prime Attributes

Definitions (source)

Prime attribute. An attribute that is part of a candidate key.

Non-prime attribute. An attribute that is not part of any candidate key.

The source's note in the keys chapter says the same thing in one line: those attributes which appear in some candidate key are called prime attributes. Note that a prime attribute must be part of some candidate key — not necessarily of the primary key you happened to choose.

7.2 The 2NF Rule: Full Functional Dependency

Definition

If we follow Second Normal Form, then every non-prime attribute must be fully functionally dependent on the primary key. That is: if X → A holds, there must be no proper subset Y of X for which Y → A also holds.

In the source's formulation, a table is in 2NF when two conditions are met:

  1. The table is in the first normal form.
  2. The primary key of the table is composed of exactly one column.
Explanation — the two statements are the same rule

The second condition looks like a different rule, and students often wonder why a single-column key automatically gives 2NF. The reason is that a single-column key has no proper subset other than the empty set, so a partial dependency is impossible. Conversely, when the key has two or more columns, a non-prime attribute might depend on only one of them — and that is exactly the violation. So “no proper subset determines the attribute” and “the key is a single column” describe the same requirement from two angles.

7.3 Partial Dependency and How to Remove It

Definition

A partial dependency exists when a non-prime attribute depends on part of a composite candidate key rather than on the whole key.

The source's Student_Project relation is the canonical example. Its prime key attributes are Stu_ID and Proj_ID. The source's slide shows only the two projections because it is illustrating the dependency, not designing the final schema. Chapter 13 builds the complete schema properly.

Explanation — the shape of a 2NF fix

Every 2NF decomposition has the same shape. Quick test for 2NF

Look at the primary key. If it has one column, the relation is automatically in 2NF (given 1NF). If it has two or more columns, check every non-prime attribute: does it need the whole key, or would one part of the key do? If one part would do, the relation is not in 2NF.

  • A partial dependency is a non-prime attribute depending on part of a composite key.
  • The fix is to split the relation so each non-prime attribute sits with the smallest key that determines it, keeping a junction relation to preserve the original relationship.

8. Third Normal Form (3NF)

Part 3  •  removing transitive dependencies

2NF removed dependencies on part of a key. 3NF removes dependencies that pass through a non-prime attribute.

8.1 The 3NF Rule

Definition

For a relation to be in Third Normal Form it must be in Second Normal Form and the following must hold: no non-prime attribute is transitively dependent on a prime key attribute.

Equivalently, for any non-trivial functional dependency X → A, either:

  • X is a super key, or
  • A is a prime attribute.

The source gives a second formulation worth keeping beside the first: the relation should comply with 2NF, and any non-prime attribute should not have a transitive functional dependency on the super key.

8.2 Transitive Dependency in a Real Relation

The source's running example for 3NF is the Student_detail relation with attributes Stu_ID, Stu_Name, Zip and City. Stu_ID is the key and the only prime attribute. City can be identified by Stu_ID, but it can also be identified by Zip itself. Since neither Zip is a super key nor City a prime attribute, and since Stu_ID → Zip → City, there is a transitive dependency.

Quick test for 3NF

For every non-trivial dependency X → A, ask: is X a super key? If yes, fine. If no, ask: is A a prime attribute? If yes, fine. If the answer to both is no, the relation is not in 3NF, and that dependency is the transitive one to break.

  • Test form: for every non-trivial X → A, either X is a super key or A is prime.
  • A transitive dependency is a chain key → non-prime → non-prime.
  • The fix moves the second-hop attributes into a table keyed by the non-prime determinant.

9. Boyce-Codd Normal Form (BCNF)

Part 3  •  3.5NF — the strictest functional form

BCNF is 3NF with the escape clause removed. Where 3NF allowed “A is prime” as an excuse, BCNF does not.

9.1 Why 3NF Is Not Always Enough

3NF permits a dependency X → A to stand even when X is not a super key, provided A is a prime attribute. That exception is usually harmless, but in one situation it leaves redundancy in place: when a non-super-key determinant determines a prime attribute that belongs to a different candidate key. BCNF closes that gap.

Explanation — the single difference

3NF: for every non-trivial X → A, either X is a super key or A is prime.
BCNF: for every non-trivial X → A, X must be a super key. (No second option.)

Because BCNF is stricter, every relation in BCNF is automatically in 3NF, but not every 3NF relation is in BCNF. The source's own framing is exactly this: BCNF is “an extension of Third Normal Form on strict terms”.

9.2 The BCNF Rule

Definition

Boyce-Codd Normal Form states that for any non-trivial functional dependency X → A, X must be a super key.

The source gives two further statements of the same rule, both worth recognising:

  • A relation is in BCNF if it holds the following conditions: the relation must be in third normal form, and for any functional dependency A → B in the relation, A should be the super key.
  • If there is a functional dependency A → B, then either A is a super key, or the dependency is trivial — that is, all the columns of B are contained in the columns of A.
Explanation — what the trivial clause means

The source illustrates the trivial clause with (course code, professor name) → (course code). This is trivially true because when you know the course code and the professor name, you obviously know the course code. Such a dependency cannot violate anything, so BCNF ignores it. Only non-trivial dependencies are tested.

The source explains the reasoning behind the rule in two sentences worth reproducing, because they show why the rule exists rather than merely what it says:

  1. A is a super key: only on a super key column should it be the case that there is a dependency of other columns. If a set of columns B can be determined by knowing some other set of columns A, then A should be a super key — a super key determines each row uniquely.
  2. It is a trivial functional dependency: there should be no non-trivial dependency of the kind that causes trouble. The source's example is that a professor's department depended on the professor's name; that creates integrity issues, because someone may edit the professor's name without changing the department, leaving the database inconsistent.

One caution belongs here, because it is a favourite viva question. Chapter 12 defines both properties precisely and tests the example above for both.

10. Fourth Normal Form (4NF)

Part 3  •  removing multivalued dependencies

Up to BCNF every rule has been about functional dependencies — “one value of X forces one value of Y”. 4NF is the first form that deals with a different situation: one value of X forcing many values of Y, independently of many values of Z.

10.1 Multivalued Dependency Revisited

Section 5.2 defined the multivalued dependency. Restate it here in the form the 4NF rule needs, because the rule is stated in terms of it.

Definition

For a relation R(A, B, C), a multivalued dependency A →→ B holds when, for each value of A, the set of B values is independent of the set of C values. In other words, A determines a set of B values and a set of C values, and the two sets have no relationship to each other. The source's three conditions for a multivalued dependency are:

  1. For a dependency A → B, if for a single value of A multiple values of B exist, the table may have a multivalued dependency.
  2. The table must have at least three columns.
  3. For R(A, B, C), if there is a multivalued dependency between A and B, then B and C must be independent of each other.

10.2 The 4NF Rule

Definition

A relation is in Fourth Normal Form if it holds all of the following conditions:

  • The relation complies with Boyce-Codd Normal Form.
  • There is no multivalued dependency between the table's attributes.

The source gives two further statements of the same rule, both useful for an exam answer:

  • For a table to satisfy 4NF: it should be in BCNF, and the table should not have any multivalued dependency.
  • In the fourth normal form: it should meet all the requirements of 3NF, and an attribute of one or more rows in the table should not result in more than one row of the same table, leading to multivalued dependencies.
Common mistake

Thinking that 4NF replaces BCNF. It does not — 4NF includes BCNF. A relation that is not in BCNF cannot be in 4NF, no matter how many multivalued dependencies you remove. State both conditions when answering.

SUBJECT →→ LECTURER

Worked step — the misleading query 
SELECT c.LECTURER, c.BOOKS

-- Select the lecturer names
SELECT c.SUBJECT, c.LECTURER
FROM   COURSE c
WHERE  c.SUBJECT = 'Mathematics';

-- Select the recommended book names
SELECT c.SUBJECT, c.BOOKS
FROM   COURSE c
WHERE  c.SUBJECT = 'Mathematics';

Firing two independent queries removes the multivalued dependency and the confusion around the data, and the table is then in 4NF. This is the same fix as Section 10.3 in a different setting: one table, one multi-valued fact.

Quick test for 4NF

Look for the cross-product pattern. If a table has three columns A, B, C and, for a single A value, every B value is paired with every C value, then B and C are independent multi-valued facts and the table is not in 4NF. The fix is always to split B and C into two tables, each keyed by A.

Chapter summary

Summary — Chapter 10
  • 4NF requires BCNF plus: no multivalued dependency among the attributes.
  • A multivalued dependency A →→ B exists when, for each A, the B values and the C values are independent sets. It needs at least three columns.
  • Its signature is a cross product in the data, and its cost is a misleading join.
  • The fix splits the table into one table per multi-valued fact, each keyed by the determinant.

11. Fifth Normal Form (5NF) and Join Dependency

Part 3  •  project–join normal form

5NF is also called the Projected Normal Form or Project–Join Normal Form (PJNF). It is the last of the six forms, and the one the source describes as “largely of academic interest” — and it explains exactly why, which is worth understanding.

11.1 The 5NF Rule

Definition

A relation R is in Fifth Normal Form if and only if every join dependency in R is implied by the candidate keys of R.

The source gives the equivalent property list, and it is the clearest way to remember the rule:

  1. R should already be in 4NF.
  2. R cannot be further non-loss decomposed — that is, it has no join dependency beyond those implied by its keys.

The source also states it in the “table” form: a table T is in fifth normal form if every join dependency in T is a consequence only of the candidate keys of T. And in plain language: a table is in 5NF if it is in 4NF and it cannot be subdivided into any smaller tables without losing some form of information.

Explanation — the phrase that matters

The whole of 5NF turns on one phrase: “implied by the candidate keys”. A table can always be split into projections and joined back — the question is whether the split is forced by the keys or whether it depends on an extra business rule. If the split is forced by the keys, the join dependency carries no new information and the table is in 5NF. If the split depends on a separate rule, that rule is a genuine constraint and the table is not in 5NF until it is decomposed.

11.2 Worked 5NF Example: Agent, Company, Product

The source's 5NF example is the table it calls agent_company product, and its explanation of the two versions of that table is the most important passage in the chapter.

The table records which agents sell which products for which companies. Suppose the business rule is:

If an agent sells a product, and the agent works for a company,
and the company makes that product — then the agent sells that product for that company.

That rule is a tuple-formation rule. It is not a key; it is an extra constraint on which rows may exist. Because such a rule exists, the join dependency

*(agent, company, product_name)

is not a consequence only of the primary key — it is also a consequence of that extra rule. That is exactly the condition the source names for a 5NF violation.

From the source — the two versions of the table

The source distinguishes two versions clearly, and the distinction is the whole point:

Version 1 — no tuple-formation rule applied. In the first example of the agent_company Product table there was no application of this rule, hence no join dependency other than that on the primary key. That table was in 5NF.

Version 2 — the rule applied. The second version of the same table violated 5NF, because the join dependency *(agent, company, product_name) was not a consequence only of the primary key, but also a consequence of the tuple-formation rule given earlier.

The lesson is precise: the same three columns can be in 5NF or not, depending on whether a tuple-formation rule exists. 5NF is about business rules, not about column lists.

11.3 Why 5NF Is Largely of Academic Interest

The source's closing assessment is refreshingly honest and should be quoted in any exam answer on 5NF:

The source's own assessment

“It can be shown that if a table is in 5NF, then, because join dependencies are the ‘ultimate’ form of dependency, it must also be in 4NF and thus conform to all the further normal forms. The problem with this is that detecting join dependencies is, in practice, very difficult. For this reason, 5NF is largely of academic interest.”

Two consequences follow. First, 5NF sits at the top of the ladder: 5NF ⟹ 4NF ⟹ BCNF ⟹ 3NF ⟹ 2NF ⟹ 1NF. Second, in ordinary application design, reaching BCNF or 3NF is usually enough; 4NF matters when independent multi-valued facts are present, and 5NF matters only when a tuple-formation rule of the kind above is in force. The source's own summary of the whole normalization chapter makes the same practical point:

“The various forms of database normalization are useful while designing the schema of a database in such a way that there is no data replication which may possibly lead to inconsistencies. 12. Lossless Decomposition

Part 3  •  the property that makes decomposition safe

Every normal form in Part 3 has been reached by splitting a relation. That raises an obvious danger: if you split a table badly, you can lose information, and no amount of tidiness in the resulting schema will compensate. The property that rules this out is lossless decomposition, and the source names it in its own definition of normalization — “decomposition which is lossless”.

12.1 What Lossless Means

Definition

A decomposition of relation R into relations R1, R2, …, Rn is lossless (more precisely, lossless-join) if joining the decomposed relations back together reproduces exactly the original relation — no rows lost, and no spurious rows created.

The word “lossless” is slightly misleading, because the danger is not only losing rows. A bad decomposition can also invent rows: the natural join of the pieces produces combinations that never existed in the original. The source's phrasing of the goal captures both directions: a relation decomposed into relations must have the lossless-join property, which ensures that no spurious or extra tuples are generated when the relations are reunited through a natural join.

12.2 The Lossless-Join Test

The test for a binary decomposition

Let R be decomposed into R1 and R2. The decomposition is lossless if and only if the common attributes R1 ∩ R2 form a super key of at least one of R1 or R2.

That is: (R1 ∩ R2) → R1  or  (R1 ∩ R2) → R2.

The intuition is worth stating plainly. The join can only match rows on the shared attributes. If those shared attributes identify a row uniquely in at least one of the pieces, the join cannot create a false match, so no spurious tuple can appear. If the shared attributes identify nothing, several rows can match each other and the cross product appears.

12.3 Worked Test on a Student Relation

Worked step — testing two decompositions

Relation: R ( Stu_ID, Stu_Name, Zip, City ), with dependencies Stu_ID → Stu_Name, Zip and Zip → City.

Decomposition A (the correct 3NF split): R1 ( Stu_ID, Stu_Name, Zip ) and R2 ( Zip, City ).

StepCheckResult

3VerdictLossless ✔

Two students with the same name would produce a false match, and the join would pair each student with the other's zip and city. Decomposition B is therefore rejected.

12.4 Dependency Preservation

Definition

A decomposition is dependency-preserving if every functional dependency of the original relation can be checked using only the resulting relations — that is, the union of the dependencies projected onto each new relation is equivalent to the original set.

Lossless join and dependency preservation are different properties, and a decomposition can have one without the other. The practical consequences are worth remembering:

Table 12.1 — The two properties and what each guarantees.
PropertyWhat it guaranteesIf it is missing
Lossless joinNo information is lost or inventedThe database now holds wrong data
Dependency preservationEvery rule can be enforced by a table constraintRules must be enforced by application code, or go unchecked
Explanation — the practical trade-off

3NF can always be achieved while preserving all dependencies. BCNF can always be achieved losslessly, but sometimes at the cost of a dependency that no single table can enforce. This is the real reason some designers stop at 3NF even though BCNF is stricter: an unenforceable rule is a worse problem than the small redundancy BCNF would have removed.

Chapter summary

Summary — Chapter 12
  • A decomposition is lossless if the natural join of the pieces reproduces the original relation exactly — no rows lost, no rows invented.
  • Test: the common attributes R1 ∩ R2 must be a super key of at least one piece.
  • A decomposition is dependency-preserving if every original dependency can be checked on the new relations.
  • 3NF can always give both properties; BCNF always gives losslessness but not always dependency preservation.

14. Denormalization

Part 3  •  deliberately adding redundancy back

Normalization is not an end in itself. It is a means to correctness, and it is paid for with joins. When joins become the bottleneck, a designer may deliberately reverse part of the normalization. The source covers this under the heading “Denormalization in Databases”, and its first sentence is the one that matters most.

14.1 Definition and Motivation

Definition (source)

Denormalization is a database optimization technique in which we add redundant data to one or more tables. This can help us avoid costly joins in a relational database.

The source adds an essential clarification: denormalization does not mean not doing normalization. It is an optimization technique that is applied after doing normalization.

The source's reasoning runs as follows. In a traditional normalized database we store data in separate logical tables and try to minimise redundant data, striving to keep only one copy of each piece of data. The benefit is obvious: if a fact changes, it changes in one place. The drawback is equally obvious: when a query needs data from several tables, the database must join them, and if the tables are large that join can take an unnecessarily long time.

14.2 A Concrete Example

The source's example is a Courses table and a Teachers table. In a normalized design each Courses row stores the teacherID for a course but not the teacherName. To list all courses with the teacher's name, the database joins the two tables.

15. Database Security: Meaning, Importance and Scope

The source makes an observation that is worth quoting in any answer about the difficulty of the subject, because it explains why security is a design problem rather than a checklist:

16. Threats and the CIA Triad

Part 4  •  what can go wrong, and how it is classified

Having established what security protects, the source turns to what threatens it. Its treatment is organised around the three properties security is meant to preserve, and around a concrete list of threat examples.

16.1 What a Threat Is

Definition (source)

A threat is any intentional or accidental event that may adversely affect the system.

Two words in that definition carry weight. Intentional covers an attacker using another person's login or a hacker entering illegally. Accidental covers a careless administrator deleting a critical file or a user mistyping a destructive statement. Security that addresses only attackers leaves half the risk untouched — and the source's physical-level discussion (Section 17.3) explicitly names administrator error as a threat.

Examples of threats (source list)

  • Using another person's log-in name to access data
  • Unauthorized copying of data
  • Program or data alteration
  • Illegal entry by a hacker
  • Viruses

16.2 Loss of Integrity, Availability and Confidentiality

The source's “Threats to databases” material is built around three losses, which together form what is usually called the CIA triad (Confidentiality, Integrity, Availability). Learn each definition exactly as the source gives it, because the wording carries the distinctions.

The three losses, in the source's words

Loss of integrity. Database integrity refers to the requirement that information be protected from improper modification. Modification of data includes creation, insertion, updating, changing the status of data, and deletion. Integrity is lost if unauthorized changes are made to the data by either intentional or accidental acts. If the loss of system or data integrity is not corrected, continued use of the contaminated system or corrupted data could result in inaccuracy, fraud, or erroneous decisions.

Loss of availability. Database availability refers to making objects available to a human user or a program to which they have a legitimate right.

Loss of confidentiality. Database confidentiality refers to the protection of data from unauthorized disclosure. The impact of unauthorized disclosure of confidential information can range from violation of the Data Privacy Act to the jeopardization of national security. Unauthorized, unanticipated, or unintentional disclosure could result in loss of public confidence, embarrassment, or legal action against the organization.

Common mistake

Treating availability as the least important of the three. The source defines it as a full member of the triad, and the reason is practical: a database that is correct and secret but unreachable has failed its users just as completely as one that has been corrupted. Note also that the source's definition is deliberately qualified — availability is owed to those with a legitimate right, not to everyone.

Physical threats cannot be prevented by clever software: a fire does not care how strong your password is. The source's statement here is short and blunt: at the operating-system level, protection from virus and worm attacks is critical. The reasoning is straightforward once the six-level model is in view. The DBMS runs on top of the operating system, so an attacker who controls the OS can read the database files directly, bypassing every DBMS control. Operating-system security is therefore not optional plumbing; it is the foundation the DBMS's own controls stand on.

A useful way to remember the levels

Ask of any proposed control: which level does it live at, and what does it assume about the levels below? Application-level authentication assumes the OS is not compromised. DBMS access control assumes the files are not readable directly. Physical locks assume nothing at all, which is why they are the last line.

18. Encryption and Key Management

Part 4  •  protecting data when the storage medium itself is lost

The source's encryption material is short but asks a good question that motivates the whole technique. It is worth following the question rather than merely listing the answer.

18.1 Why Encrypt

The source's motivating scenario: what if a laptop, disk or USB key with critical data is lost?

Notice why this scenario defeats the controls discussed so far. Access control and authentication protect data while the DBMS is running and reachable. But a lost disk is not a running database — it is a physical object in a stranger's hands. No password prompt stands between the finder and the bytes. The only control that helps is one that makes the bytes meaningless without a secret.

18.2 Storage-Level Encryption and Key Management

The source's approach

Partial solution: encrypt the database at storage level, transparent to the application.

Main issue: key management.

Common practice: the user provides a decryption key (password) when the database is started up. This is supported by many database systems.

The phrase “transparent to the application” is the design goal. The application continues to issue ordinary SQL; the DBMS encrypts on write and decrypts on read. This means no application change is needed — but it also means the encryption cannot protect against an attacker who is already inside the running database with valid credentials, because at that point the DBMS is decrypting for them.

Explanation — why key management is the hard part

Encryption itself is a solved problem; keeping the key safe is not. The source names key management as the main issue for three connected reasons:

  • The key must be available when the database starts, so it cannot simply be stored beside the data — a lost disk would then carry its own key.
  • If the key is supplied by a person as a password at startup, the system is only as secure as that person and that password (see Section 20.2).
  • If the key is lost, the data is permanently unreadable. Encryption converts a confidentiality risk into an availability risk, which is exactly the tension described in Figure 16.1.

18.3 Practical Guidance from the Source

The source's closing guidance on encryption is a practice, not a theory: it is standard practice now to encrypt credit card information, and other sensitive information. The reason is the same as the motivating scenario — credit card numbers are precisely the data whose disclosure is most damaging and whose storage medium is most likely to travel (laptops, backups, portable drives).

Common mistake

Believing that encryption makes a database secure on its own. Encryption protects data at rest — the bytes on the medium. It does nothing about an attacker who logs in with valid credentials, nothing about a careless user who reads data they are authorized to read, and nothing about an application that is tricked into revealing data. Encryption is one control among the six in Chapter 21, not a substitute for the others.

Chapter summary

Summary — Chapter 18
  • Encryption is motivated by loss of the storage medium itself, which no access-control mechanism can prevent.
  • The approach is storage-level encryption that is transparent to the application.
  • The main problem is key management: the key must be available at startup yet not stored with the data, and losing it means losing the data.
  • It is now standard practice to encrypt credit card and other sensitive information.

Authentication: who are you? Prove it!

Using the two words interchangeably. An answer that says “authentication controls what a user can access” is wrong in a way that costs marks. Authentication answers who; authorization answers what. Keep the order in mind: authentication is always completed first.

19.2 Discretionary Access Control (DAC)

Definition (source)

Discretionary Access Control: users have control over their own data, and permissions are granted using Access Control Lists (ACLs).

The source adds the mechanism: the typical method of enforcing DAC in a database system is based on granting and revoking privileges. These are used to grant privileges to users, including the capability to access specific data files, records or fields in a specified mode — such as read, insert, delete, or update.

The word “discretionary” is the key: the owner of the data decides who else may use it. That flexibility is also the model's weakness, because a user who can read a table can usually copy it somewhere the owner no longer controls.

19.3 Mandatory Access Control (MAC)

Definition (source)

Mandatory Access Control is based on a central authority assigning security labels to data and users. These labels define access levels, ensuring that users can only access data classified within their clearance level. MAC is commonly used in government and military applications, where strict control over data access is required.

The decisive difference from DAC is that the individual user has no discretion at all. A clearance level and a classification label are compared by the system, and the comparison — not the owner's preference — decides access. This is the model that implements the “top secret, secret, confidential, unclassified” hierarchy the source mentioned under multiple security levels.

19.4 Role-Based Access Control (RBAC)

Definition (source)

Role-Based Access Control is based on predefined roles assigned to users. Each role has specific privileges, including the ability to read, insert, delete, or update data. Instead of granting permissions to individual users, RBAC assigns access based on job responsibilities, making it efficient for large organizations.

RBAC's advantage is administrative. In a large organization, granting privileges user by user means repeating the same grants hundreds of times and updating them whenever someone changes jobs. Granting a role once and assigning users to it means the permissions are described in one place.

20. Network and Human-Level Security

Part 4  •  protecting data in transit, and the weakest link

The two outer levels of Figure 17.1 need their own treatment, because the attacks there are unlike the ones a DBMS can handle internally. On the network, data is in transit and can be intercepted; at the human level, the credential itself can be guessed or shared.

20.1 Network-Level Threats

The source's network-level material

At the network level, encryption must be used to prevent:

  • Eavesdropping — unauthorized reading of messages.
  • Masquerading — pretending to be an authorized user or legitimate site, or sending messages supposedly from authorized users.

These are handled by secure HTTP — https://. It must also prevent person-in-the-middle attacks: for example, someone impersonates the seller or the bank/credit-card company and fools the buyer into revealing information.

Explanation — why one control covers three attacks

All three attacks fail against the same thing: a channel whose contents cannot be read and whose endpoints can be authenticated. Eavesdropping fails because the attacker cannot read the ciphertext. Masquerading and person-in-the-middle fail because the client can verify that it is talking to the real server, not an impostor. That is precisely what https:// provides — encryption plus server authentication.

20.2 Passwords

The source's point

Password. Most users abuse passwords. For example: they choose easy-to-guess passwords, and they share passwords with others.

The source's phrasing is deliberately blunt, and the two failures it names are worth separating because they have different fixes:

Table 20.1 — The two password failures the source names, and the control for each.
FailureWhy it is dangerousCharacteristic control
Easy-to-guess passwordAn attacker can guess it without any technical attack at allPassword policy: length, complexity, expiry
Sharing passwords with othersDestroys the link between identity and person — authentication still succeeds, but it no longer means what it shouldPolicy plus audit; technical controls cannot detect consent
Common mistake

Thinking that password sharing is a minor issue. It breaks the entire basis of authentication: every later control assumes the identity is genuine. If three people use one login, no access-control decision — and no audit trail — can be trusted.

20.3 Smartcards

The source's point

Smartcards. Need the smartcard itself, plus a PIN or password.

A smartcard adds a second factor: something the user has, combined with something the user knows. This directly addresses both password failures. A shared password is no longer enough, because the attacker also needs the physical card; and a guessed password is no longer enough for the same reason. The source's “Bill Gates” note in the slide is the memorable illustration of the residual risk — a smartcard can be lost or stolen, and if the PIN is written down beside it, both factors travel together.

The security principle here

Two independent factors are stronger than one, because the two failure modes are independent. A password can be guessed or shared but not stolen from your pocket; a card can be stolen but not guessed. Requiring both means an attacker must succeed at two different kinds of attack.

21. Control Methods of Database Security

Part 4  •  the six measures that actually implement security

Chapters 15 to 20 described what is threatened and where. This chapter is the answer: the six control measures the source names, each defined and then tied back to the threat it addresses.

21.1 The Six Control Measures

The source's list

The following are the main control measures used to provide security of data in databases:

  1. Authentication
  2. Access control
  3. Inference control
  4. Flow control
  5. Database security applying statistical method
  6. Encryption

21.2 Authentication

Definition (source)

Authentication is the process of confirming whether the user logs in according to the rights provided to them to perform the activities of the database. A particular user can log in only up to their privilege, and cannot access other sensitive data. The privilege of accessing sensitive data is restricted by using authentication.

By using authentication tools such as biometrics — retina and fingerprints — the database can be protected from unauthorized or malicious users.

Read the source's wording carefully, because it makes a claim that is easy to misstate. Authentication restricts the privilege of accessing sensitive data, but it does not by itself decide what a user may do — that is authorization (Section 19.1). Authentication is the gate: it establishes who is asking.

21.3 Access Control

Definition (source)

The security mechanism of a DBMS must include provisions for restricting access to the database by unauthorized users. Access control is done by creating user accounts and controlling the login process through the DBMS, so that access to sensitive data is possible only for those database users who are allowed to access such data, and access by unauthorized persons is restricted.

The database system must also keep track of all operations performed by a certain user throughout the entire login time.

Two distinct duties are named here, and both matter:

Table 21.1 — The two duties of access control.
DutyWhat it meansWhy it matters
Restrict accessCreate accounts; decide, per user, what may be read, inserted, deleted or updatedPrevents unauthorized reading and modification
Track operationsKeep a record of everything a user did during the whole login sessionMakes after-the-fact investigation possible, and deters misuse by insiders

The three access-control models that implement the first duty — DAC, MAC and RBAC — were covered in Sections 19.2 to 19.4. The second duty is what is usually called auditing, and the source mentions it as one of the four security measures alongside access controls, encryption and authentication (Section 15.1).

21.4 Inference Control

Definition (source)

Inference control is the countermeasure to the statistical-database security problem. It is used to prevent the user from completing any inference channel, and it protects sensitive information from indirect disclosure. Inferences are of two types: identity disclosure or attribute disclosure.

The threat inference control addresses is subtle and worth spelling out. No individual query breaks a rule. Each answer is a legitimate statistic about a group. But a sequence of legitimate answers can be combined to reveal a fact about one person — a fact that no single query was allowed to return.

Worked step — how inference leaks a secret

Suppose the rule is that no query may return data about a single employee's salary.

Q1: SELECT AVG(salary) FROM emp;                         -- average over 100 employees: fine
Q2: SELECT AVG(salary) FROM emp WHERE dept = 'CSE';      -- average over 40: fine
Q3: SELECT AVG(salary) FROM emp WHERE dept = 'CSE'
      AND name <> 'Ananya';                            -- average over 39: fine

Each query is a statistic over a group, so each is permitted. But Q2 and Q3 together let the questioner solve for Ananya's salary exactly:

salary(Ananya) = 40 × AVG(Q2) − 39 × AVG(Q3)

The sensitive value has been disclosed without any single query violating the rule. That is indirect disclosure, and inference control exists to prevent it — for example by refusing queries whose result set is too small.

21.5 Flow Control and Covert Channels

Definition (source)

Flow control prevents information from flowing in a way that reaches unauthorized users. The pathways by which information flows implicitly in ways that violate the privacy policy of a company are called covert channels.

Note the difference from access control. Access control asks “may this user read this item?” Flow control asks “may this fact move from where it is to where this user is?” A user might be perfectly entitled to read two separate values yet not entitled to the combination — for example, entitled to see project codes and entitled to see salaries, but not the mapping between them. Flow control restricts the propagation of information rather than the access to objects.

From the source — a terminology note

The source writes “convert channels”. The standard term in the security literature is covert channels, and the source's own definition (“pathways for information to flow implicitly in ways that violate the privacy policy”) is the standard definition of a covert channel. These notes use “covert channel” and note the source's spelling here so that you recognise both.

21.6 Statistical Database Security

Definition (source)

Statistical database security focuses on the protection of confidential individual values stored in and used for statistical purposes, and used to retrieve summaries of values based on categories. It does not permit retrieval of individual information.

It allows access to the database to get statistical information — such as the number of employees in the company — but not to access the detailed confidential or personal information about a specific individual employee.

The source's example is the clearest way to hold the distinction: a count of employees is permitted; one employee's salary is not. The permitted class is aggregate; the forbidden class is individual. Inference control (Section 21.4) is the mechanism that keeps the boundary intact when a clever sequence of aggregates threatens to cross it.

21.7 Encryption

Definition (source)

Encryption is mainly used to protect sensitive data such as credit card numbers, OTP numbers, and other sensitive numbers. The data is encoded using encoding algorithms.

Chapter 18 covered encryption in detail, including the key-management problem that makes it harder than it looks. In the list of six controls, encryption's distinct role is that it is the only one that still works when the database is not running — that is, when the attacker holds the storage medium rather than a session.

22. The DBA, Privileges and Statistical Database Security

Part 4  •  who owns the security policy

Every control in Chapter 21 needs an administrator. The source closes its security material by describing that role, because the controls are only as good as the authority that assigns them.

22.1 Who the DBA Is

Definition (source)

The database administrator (DBA) is the central authority for managing a database system, and is responsible for the overall security of the database system.

The phrase “central authority” connects directly to the access-control models of Chapter 19. In DAC the DBA is the source of grants; in MAC the DBA is the central authority that assigns security labels; in RBAC the DBA defines the roles. Whichever model is in use, someone must hold the authority to make the initial decisions, and that is the DBA.

22.2 DBA Responsibilities

Responsibilities (source)

The DBA's responsibilities include:

  • Granting privileges to users who need to use the system.
  • Classifying users and data in accordance with the policy of the organization.

The DBA is responsible for the overall security of the database system.

The two responsibilities map onto the two ideas already established. Granting privileges is the discretionary act — DAC's granting and revoking (Section 19.2). Classifying users and data is the mandatory act — assigning the security labels and clearance levels of MAC (Section 19.3). A DBA therefore operates in both worlds at once.

22.3 The DBA / Superuser Account

The DBA account (source)

The DBA has a DBA account in the DBMS. Sometimes these are called a system or superuser account. These accounts provide powerful capabilities such as:

  1. Account creation
  2. Privilege granting
  3. Privilege revocation
  4. Security level assignment

Action 1 is access control, whereas actions 2 and 3 are discretionary access, and action 4 is used to control mandatory authorization.

Common mistake

Treating the DBA account as just another user account. The source calls its capabilities “powerful”, and the reason is that it can create accounts, grant and revoke privileges, and assign security levels. An attacker who obtains the DBA account does not need to defeat any control — the attacker is the control. This is why DBA credentials require the strongest protection in the system.

Two SQL*Plus conveniences appear in almost every example in the source, and understanding them prevents a lot of confusion when you run the programs yourself.

24. Conditional Control: IF and CASE

Part 5  •  choosing which statements run

The source states the purpose in one sentence: PL/SQL allows the use of an IF statement to control the execution of a block of code. The IF-THEN-ELSIF-ELSE-END IF construct allows specifying certain conditions under which a specific block of code should be executed. This chapter covers the four IF forms and the CASE statement.

24.1 IF-THEN

Syntax 
IF condition
THEN
   statement;
END IF;

Use it when: statements should execute only when the condition is true, and there is nothing to do otherwise.

24.2 IF-THEN-ELSE

Syntax 
IF condition
THEN
   [statements to execute when condition is TRUE]
ELSE
   [statements to execute when condition is FALSE]
END IF;

Use it when: one set of statements should execute when the condition is true, and a different set when it is false.

24.3 IF-THEN-ELSIF

Syntax 
IF condition1
THEN
   statements to execute when condition1 is TRUE
ELSIF condition2
THEN
   statements to execute when condition2 is TRUE
END IF;

Use it when: one set of statements should execute when condition1 is true, or a different set when condition2 is true.

24.4 IF-THEN-ELSIF-ELSE

Syntax 
IF condition1
THEN
   statements to execute when condition1 is TRUE
ELSIF condition2
THEN
   statements to execute when condition2 is TRUE
ELSE
   statements to execute when both condition1 and condition2 are FALSE
END IF;

Use it when: there are three or more outcomes — one for condition1, one for condition2, and one for neither.

Common mistake

Writing ELSE IF (two words) instead of ELSIF (one word). ELSE IF opens a nested IF statement that then needs its own END IF;, and the block will not compile without it. In PL/SQL the multi-way branch keyword is ELSIF.

24.5 The CASE Statement

Definition and syntax (source)

The PL/SQL CASE statement provides the facility to execute a sequence of statements based on a selector. A selector may be a variable, a function, or an expression.

CASE [expression]
   WHEN condition1 THEN result1
   WHEN condition2 THEN result2
   …
   WHEN condition_n THEN result_n
   ELSE result
END;

CASE and the IF ladder solve the same problem — choosing one branch from several — but they read differently. Use CASE when every branch tests the same value against a list of possibilities; use the IF ladder when the conditions are unrelated expressions.

24.6 Worked Conditional Programs

Program 1 — IF-THEN-ELSE (source Example 1)

   a number(3) := 200;

      -- if condition is true then print the following
      dbms_output.put_line('a is less than 10 ' );
   ELSE
      dbms_output.put_line('a is not less than 10 ' );
   END IF;
   dbms_output.put_line('value of a is : ' || a);
END;

Dry run: a is initialised to 200. The test a < 10 is false (200 is not less than 10), so the ELSE branch runs. Control then continues after END IF and the final PUT_LINE runs unconditionally.

25. Iterative Control: LOOP, WHILE and FOR

Part 5  •  repeating statements — and knowing when to stop

The source introduces the topic precisely: LOOP statements let you execute a sequence of statements multiple times. There are three forms of LOOP statements: LOOP, WHILE-LOOP, and FOR-LOOP. The three forms differ in one crucial respect — where the condition is tested, and therefore whether the body can run zero times.

25.1 The Basic LOOP

Syntax (source) 
LOOP
   sequence_of_statements
END LOOP;

The simplest form of LOOP statement is the basic (or infinite) loop, which encloses a sequence of statements between the keywords LOOP and END LOOP. With each iteration the sequence is executed, then control resumes at the top of the loop.

Note the source's parenthetical: it calls this the “infinite” loop, and the label is fair — nothing in the syntax itself stops it. A basic LOOP terminates only when an EXIT statement executes inside it.

25.2 EXIT and EXIT-WHEN

EXIT (source)

If further processing is undesirable or impossible, you can use an EXIT statement to complete the loop. You can place one or more EXIT statements anywhere inside a loop, but nowhere outside a loop.

EXIT forces a loop to complete unconditionally. When an EXIT statement is encountered, the loop completes immediately and control passes to the next statement.

LOOP
   ...
   IF credit_rating < 3 THEN
      ...
      EXIT;   -- exit loop immediately
   END IF;
END LOOP;
-- control resumes here
EXIT-WHEN (source)

EXIT-WHEN lets a loop complete conditionally. When the EXIT statement is encountered, the condition in the WHEN clause is evaluated. If the condition is true, the loop completes and control passes to the next statement after the loop.

LOOP
   FETCH c1 INTO ...;
   EXIT WHEN c1%NOTFOUND;   -- exit loop if condition is true
   ...
END LOOP;
CLOSE c1;

The source adds an essential observation about termination: until the condition is true, the loop cannot complete. So, a statement inside the loop must change the value of the condition. In the FETCH example, if the FETCH returns a row the condition is false; when the FETCH fails to return a row the condition becomes true, the loop completes, and control passes to the CLOSE statement.

EXIT-WHEN replaces a simple IF — the source's own comparison

These two fragments are logically equivalent, but the second is easier to read:

Using IFUsing EXIT-WHEN
IF count > 100 THEN
   EXIT;
END IF;		EXIT WHEN count > 100;

This is a good example of a PL/SQL idiom worth adopting: when a loop's only purpose for an IF is to exit, use EXIT WHEN instead.

Common mistake — EXIT outside a loop

The source makes the point with a deliberately wrong example:

BEGIN
   ...
   IF credit_rating < 3 THEN
      ...
      EXIT;   -- NOT ALLOWED
   END IF;
END;

EXIT must be placed inside a loop. To complete a PL/SQL block before its normal end is reached, use the RETURN statement instead. The distinction is: EXIT leaves a loop; RETURN leaves a subprogram or block.

25.3 Loop Labels and Nested Loops

Labels (source)

Like PL/SQL blocks, loops can be labelled. The label is an undeclared identifier enclosed by double angle brackets, and it must appear at the beginning of the LOOP statement:

<<label_name>>
LOOP
   sequence_of_statements
END LOOP;

Optionally, the label name can also appear at the end of the LOOP statement:

<<my_loop>>
LOOP
   ...
END LOOP my_loop;

When you nest labelled loops, use ending label names to improve readability. More importantly, labels give you a way to exit more than one loop at once:

<<outer>>
LOOP
   ...
   LOOP
      ...
      EXIT outer WHEN ...;   -- exit both loops
   END LOOP;
   ...
END LOOP outer;
Explanation — what EXIT outer does

The source states the effect precisely: every enclosing loop up to and including the labelled loop is exited. So EXIT outer from the inner loop does not merely leave the inner loop — it leaves the inner loop and the outer loop in one step, landing on the statement after END LOOP outer;. This is the clean way to break out of deeply nested processing without setting and testing flag variables.

25.4 WHILE-LOOP

Syntax (source) 
WHILE condition LOOP
   sequence_of_statements
END LOOP;

Before each iteration of the loop the condition is evaluated. If the condition is true the sequence is executed, then control resumes at the top of the loop. If the condition is false or null, the loop is bypassed and control passes to the next statement.

The source gives a worked illustration and draws out the crucial consequence:

WHILE total <= 25000 LOOP
   ...
   SELECT sal INTO salary FROM emp WHERE ...;
   total := total + salary;
END LOOP;
Explanation — the number of iterations is unknown in advance

The source's own words: the number of iterations depends on the condition and is unknown until the loop completes. The condition is tested at the top of the loop, so the sequence might execute zero times. In the last example, if the initial value of total is larger than 25000, the condition is false and the loop is bypassed.

This is the single most important fact about WHILE: zero iterations is a legitimate outcome.

25.5 Building a Loop-That-Runs-At-Least-Once

The source notes that some languages have a LOOP UNTIL or REPEAT UNTIL structure which tests the condition at the bottom, so the body always executes at least once. PL/SQL has no such structure — but you can build one, and the source shows both ways.

Method 1 — a basic LOOP with EXIT WHEN at the bottom 
LOOP
   sequence_of_statements
   EXIT WHEN boolean_expression;
END LOOP;

Because the EXIT WHEN is the last thing in the body, the body always runs at least once before the test is reached. This is the closest PL/SQL equivalent of REPEAT UNTIL.

Method 2 — a WHILE loop with an initialised Boolean flag 
done := FALSE;
WHILE NOT done LOOP
   sequence_of_statements
   done := boolean_expression;
END LOOP;

The flag starts FALSE, so NOT done is true on the first test and the body runs. At the end of the body the flag is recomputed. The source's warning is important: a statement inside the loop must assign a new value to the Boolean variable. Otherwise you have an infinite loop.

A fact worth remembering

The source points out that these two loops are logically equivalent — a WHILE whose condition is always true is just a basic loop:

Always-true WHILEBasic LOOP
WHILE TRUE LOOP
  ...
END LOOP;		LOOP
  ...
END LOOP;

25.6 FOR-LOOP and REVERSE

Syntax (source) 
FOR counter IN [REVERSE] lower_bound..higher_bound LOOP
   sequence_of_statements
END LOOP;

Whereas the number of iterations through a WHILE loop is unknown until the loop completes, the number of iterations through a FOR loop is known before the loop is entered. FOR loops iterate over a specified range of integers. The range is part of an iteration scheme enclosed by the keywords FOR and LOOP, and a double dot (..) serves as the range operator.

The rule that catches people out

The range is evaluated when the FOR loop is first entered and is never re-evaluated. This means the bounds are computed once. If a variable used as a bound changes inside the loop, the number of iterations does not change.

The three behaviours of a FOR loop

Table 25.1 — FOR loop behaviour in the three cases the source illustrates.
CaseCodeValues of the counterIterations
Normal, ascendingFOR i IN 1..3 LOOP1, 2, 33
Lower = upperFOR i IN 3..3 LOOP31
REVERSEFOR i IN REVERSE 1..3 LOOP3, 2, 13
Common mistake — writing REVERSE bounds backwards

With REVERSE, iteration proceeds downward from the higher bound to the lower bound, and after each iteration the loop counter is decremented. But you still write the range bounds in ascending order, not descending. So FOR i IN REVERSE 1..3 is correct and gives 3, 2, 1 — while FOR i IN REVERSE 3..1 is not the way to write it. The source states this explicitly: “you write the range bounds in ascending (not descending) order.”

Common mistake — assigning the FOR counter

Inside a FOR loop the loop counter can be referenced like a constant but cannot be assigned values. The source's example shows both what is legal and what is not:

FOR ctr IN 1..10 LOOP
   IF NOT finished THEN
      INSERT INTO ... VALUES (ctr, ...);   -- legal: reading ctr
      factor := ctr * 2;                   -- legal: reading ctr
   ELSE
      ctr := 10;                           -- NOT ALLOWED: assigning ctr
   END IF;
END LOOP;

The reason is that the loop itself controls the counter. If your body could change it, the loop's iteration count would no longer match the range, and the guarantee that a FOR loop runs exactly once per integer in the range would be broken.

26. Sequential Control: GOTO and NULL

Part 5  •  the two statements you should rarely need

The source opens this topic with a candid assessment that is worth reading before the syntax: the GOTO statement is seldom needed. Occasionally, it can simplify logic enough to warrant its use. The NULL statement can improve readability by making the meaning and action of conditional statements clear. Overuse of GOTO statements can result in code that is hard to understand and maintain. Use GOTO statements sparingly.

That framing matters, because a student who only learns the syntax may conclude that GOTO is a normal tool. It is not: it is an escape hatch for unusual situations, and the source's own advice is to prefer an exception handler when branching out of deeply nested structure.

26.1 The GOTO Statement

Definition (source)

The GOTO statement branches to a label unconditionally. The label must be unique within its scope and must precede an executable statement or a PL/SQL block. When executed, the GOTO statement transfers control to the labelled statement or block. The labelled statement or block can be down or up in the sequence of statements.

GOTO label;
..
..
<< label >>
statement;

The source's description in the second paragraph is the same rule in plainer words: a GOTO statement in PL/SQL provides an unconditional jump from the GOTO to a labelled statement in the same subprogram. The phrase “in the same subprogram” is important — it is the first of the restrictions in Section 26.3.

Program 1 — primality test with GOTO (source)

Problem: test whether n is prime, using GOTO to skip the “is prime” message when a divisor is found.

   p VARCHAR2(30);
   n PLS_INTEGER := 37;   -- test any integer > 2 for prime
BEGIN
   FOR j in 2..ROUND(SQRT(n)) LOOP
      IF n MOD j = 0 THEN          -- test for prime
         p := ' is not a prime number';   -- not a prime number
         GOTO print_now;
      END IF;
   END LOOP;
   p := ' is a prime number';

   <<print_now>>
   DBMS_OUTPUT.PUT_LINE(TO_CHAR(n) || p);

/

Logic: the loop tests every integer from 2 up to √n. If any of them divides n exactly, the message is set to “not prime” and control jumps straight to the label, skipping the loop's remaining iterations and the “is prime” assignment. If the loop finishes without finding a divisor, execution falls through to p := ' is a prime number' and then reaches the label naturally.

Why this use of GOTO is defensible

This is the kind of case the source means by “occasionally it can simplify logic”. The alternative without GOTO would be a Boolean flag set in the loop and tested afterwards. The GOTO version is shorter, and the label sits immediately after the loop, so the jump distance is tiny and the control flow is easy to follow. Note also the detail that makes the program correct: the label must precede an executable statement, which is why it sits directly above DBMS_OUTPUT.PUT_LINE and not on a blank line.

26.3 Restrictions on GOTO

The source lists the restrictions explicitly. They are a favourite examination question, and they all follow from one principle: GOTO may not jump into the middle of a structured construct, nor out of a subprogram.

Restrictions (source)
  • A GOTO statement cannot branch into an IF statement, CASE statement, LOOP statement or sub-block.
  • A GOTO statement cannot branch from one IF statement clause to another, or from one CASE statement WHEN clause to another.
  • A GOTO statement cannot branch from an outer block into a sub-block (that is, an inner BEGIN-END block).
  • A GOTO statement cannot branch out of a subprogram. To end a subprogram early, either use the RETURN statement or have GOTO branch to a place right before the end of the subprogram.
  • A GOTO statement cannot branch from an exception handler back into the current BEGIN-END block. However, a GOTO statement can branch from an exception handler into an enclosing block.
Common mistake — the asymmetric exception-handler rule

The last restriction is the one most often misremembered, because it is not symmetric. A GOTO cannot branch from an exception handler back into the current BEGIN-END block — but it can branch from an exception handler into an enclosing block. The logic is that jumping back in would re-enter a block whose execution had already failed, which is precisely the situation the exception handler exists to deal with.

26.4 The NULL Statement

Definition (source)

The NULL statement does nothing and passes control to the next statement. Some languages refer to such an instruction as a no-op (no operation).

The source's framing of its purpose is what makes it worth knowing: the NULL statement can improve readability by making the meaning and action of conditional statements clear. Its value is not that it does anything, but that it says that nothing should be done — which is different from forgetting to write anything.

Because the ELSE branch is documented intent. A reader of this block can see immediately that the case was considered and deliberately left alone, rather than overlooked. An empty ELSE (or no ELSE at all) leaves the reader wondering. This is exactly the readability benefit the source names.

27. Cursors: Concept and Implicit Cursors

Part 6  •  working with a result set one row at a time

A cursor exists to solve a mismatch. SQL is set-oriented: a query returns a whole set of rows at once. A procedural program is row-oriented: it does one thing at a time. Something must bridge the two, and in PL/SQL that something is the cursor.

27.1 What a Cursor Is

Definition (source)

A PL/SQL cursor is a pointer that points to the result set of an SQL query against database tables.

The source explains why it is needed: when you work with an Oracle database, you work with a complete set of rows returned from a SELECT statement. However, the application in some cases cannot work effectively with the entire result set. Therefore the database server needs to provide a mechanism for the application to work with one row, or a subset of the result set, at a time. Oracle created the PL/SQL cursor to provide these extensions.

The single word to hold on to is pointer. A cursor is not the data; it is a position within the data. Each fetch moves the pointer forward one row, and the program acts on whatever row the pointer currently indicates.

27.2 The Context Area and the Active Set

The source's explanation

Oracle has dedicated memory locations for executing SQL statements, and holds that processed information — for example, the total number of rows updated. A cursor in PL/SQL gives a name and acts as a pointer to the area of work called a context area, and then uses its information. It keeps the number of rows processed by the SQL statement. These rows are called the active set. The size of the active set is equal to the count of the rows that meet the condition.

27.3 Implicit Cursors

Definition (source)

Implicit cursors are automatically created by Oracle whenever an SQL statement is executed, when there is no explicit cursor for the statement. Programmers cannot control the implicit cursors and the information in them.

Whenever a DML statement (INSERT, UPDATE and DELETE) is issued, an implicit cursor is associated with that statement. For INSERT operations, the cursor holds the data that needs to be inserted. For UPDATE and DELETE operations, the cursor identifies the rows that would be affected.

Three consequences follow, and they are worth stating separately because exam questions often probe them:

  1. You do not declare an implicit cursor. Oracle creates it for you whenever you run a DML statement or a SELECT … INTO.
  2. You do not open or close it. Oracle manages its whole life cycle, and closes it automatically after executing the associated statement.
  3. You can read its attributes. This is the part that makes implicit cursors useful. The attributes tell you what the statement just did.

27.4 Implicit Cursor Attributes

The SQL cursor (source)

In PL/SQL you can refer to the most recent implicit cursor as the SQL cursor, which always has attributes such as %FOUND, %ISOPEN, %NOTFOUND and %ROWCOUNT. The SQL cursor has additional attributes, %BULK_ROWCOUNT and %BULK_EXCEPTIONS, designed for use with the FORALL statement.

Any SQL cursor attribute is accessed as sql%attribute_name.

28. Explicit Cursors and Cursor Loops

An implicit cursor is convenient but opaque: you can read its attributes, but you cannot control it. When a program needs real control over a multi-row query — reading rows one at a time, deciding when to stop — it needs an explicit cursor.

28.1 Declaring, Opening, Fetching and Closing

Definition (source)

Explicit cursors are programmer-defined cursors for gaining more control over the context area. An explicit cursor should be defined in the declaration section of the PL/SQL block. It is created on a SELECT statement which returns more than one row.

  4. Closing the cursor, to release the allocated memory.

Program — reading the CUSTOMERS table (source)

   c_addr  customers.address%type;

      SELECT id, name, address FROM customers;

After the loop the cursor is closed.

Placing the EXIT immediately after the FETCH means the loop stops the moment a fetch finds no row, and never prints an uninitialised row. 28.5 Cursor Errors and Exam Traps

Common mistake 1 — forgetting to open the cursor

Fetching from a cursor that has not been opened raises ORA-01001: invalid cursor. The OPEN statement is what allocates the context area; without it there is nothing to fetch from.

Common mistake 2 — testing %NOTFOUND before the first fetch

Immediately after OPEN, the cursor has not fetched anything, so %FOUND and %NOTFOUND do not yet reflect the data. The reliable pattern — the one the source uses — is FETCH first, then EXIT WHEN c%NOTFOUND. A loop that tests %NOTFOUND before its first fetch may process one row too many or too few.

Common mistake 3 — forgetting to close

An unclosed cursor keeps its context area allocated until the session ends. In a program that opens many cursors, that is a memory leak. CLOSE c_customers; releases the memory, and the source places it after the loop for exactly this reason.

Common mistake 4 — a cursor for a query that returns one row

The source specifies that an explicit cursor “is created on a SELECT Statement which returns more than one row”. If a query is guaranteed to return a single row, SELECT … INTO with an implicit cursor is the simpler and more appropriate tool. Using a cursor loop for a single row works but adds ceremony for no benefit.

The pattern to memorise 
CURSOR c IS SELECT … ;      -- declare (in DECLARE section)
…
OPEN  c;                    -- allocate
LOOP
   FETCH c INTO …;          -- get the next row
   EXIT WHEN c%NOTFOUND;    -- stop when there is none
   … process the row …      -- only reached for a real row
END LOOP;
CLOSE c;                    -- release

Every explicit cursor program in this chapter, and in the source, is a variation on these six lines.

Summary — Chapter 28

  • The four steps are declare (initialise memory), open (allocate memory), fetch (retrieve one row at a time) and close (release memory).
  • A cursor loop fetches, tests %NOTFOUND to decide whether to stop, and processes the row. The EXIT WHEN must come immediately after the FETCH.
  • Explicit cursors are closed by you; implicit cursors are closed by Oracle, which is why SQL%ISOPEN is always FALSE.
  • Common errors: fetching without opening, testing %NOTFOUND before the first fetch, forgetting to close, and using a cursor where a single-row SELECT … INTO would do.

29. SQL Views: Concept and Creation

Part 7  •  a stored query that behaves like a table

A view is the database's answer to a common problem: many different users need to see different slices of the same data, but you do not want to maintain a separate copy for each. A view stores the question, not the answer — and every time it is used, the question is asked again against the current data.

29.1 Definition and Base Tables

Definition (source)

An SQL View is a specific representation of data from one or more tables. The tables referred to in the view are known as base tables. Creating a view does not take any storage space, because only the query is stored in the data dictionary and the actual data is not stored anywhere.

The maximum number of columns that can be defined in a SQL View is 1000, as in tables.

The source also gives the informal framing that is worth holding alongside the formal one: views in SQL are kind of virtual tables. A view also has rows and columns as they are in a real table in the database. We can create a view by selecting fields from one or more tables present in the database. A view can either have all the rows of a table or specific rows based on a certain condition.

Explanation — why “no storage space” is a real benefit

Because only the query is stored, a view cannot become inconsistent with its base tables. There is no second copy to fall out of date — the source's phrase is that the actual data “is not stored anywhere”. This is the opposite of the redundancy problem of Part 3: a view is a form of reuse that adds no redundancy at all.

29.2 Benefits of Views

Benefits (source)

The reasons for using views in applications can be many, like:

  • Reducing complexity.
  • Improving security.
  • Renaming the table columns.

30.1 Dropping a View

Syntax (source)

30.3 Conditions Required to Update a View

This is the most examinable part of the chapter, and the source states it as a numbered list of five conditions. The framing is important: there are certain conditions needed to be satisfied to update a view. If any one of these conditions is not met, then we will not be allowed to update the view.

The five conditions (source, verbatim intent)
  1. The SELECT statement which is used to create the view should not include a GROUP BY clause or an ORDER BY clause.
  2. The SELECT statement should not have the DISTINCT keyword.
  3. The View should have all NOT NULL values.
  4. The view should not be created using nested queries or complex queries.
  5. The view should be created from a single table. If the view is created using multiple tables, we will not be allowed to update the view.
Explanation — a good way to remember the five

Notice that the five conditions all answer the same question: can the DBMS work out which base-table row this view row came from? GROUP BY and DISTINCT collapse several base rows into one, so the answer is no. A join mixes two tables, so there is no single row. A nested or complex query hides the mapping behind intermediate steps. And an ORDER BY says nothing about identity at all. If you remember the one question, you can reconstruct the five conditions in an examination.

30.6 WITH CHECK OPTION

Definition (source)

The WITH CHECK OPTION clause in SQL is a very useful clause for views. It is applicable to an updatable view. If the view is not updatable, then there is no meaning in including this clause in the CREATE VIEW statement.

  • The WITH CHECK OPTION clause is used to prevent the insertion of rows in the view where the condition in the WHERE clause in the CREATE VIEW statement is not satisfied.
  • If we have used the WITH CHECK OPTION clause in the CREATE VIEW statement, and if the UPDATE or INSERT clause does not satisfy the conditions, then they will return an error.

This is a genuinely useful mechanism, and its purpose is easy to state. A view's WHERE clause defines which rows belong to the view. Without WITH CHECK OPTION, you can insert a row through the view that does not satisfy that condition — and the row then vanishes from the view the moment it is inserted, because the view's query excludes it. WITH CHECK OPTION forbids that, turning a silent disappearance into an explicit error.

Example — SampleView with WITH CHECK OPTION (source)

Problem: create a view of students whose NAME is not null, and prevent any insert that would violate that condition.

CREATE VIEW SampleView AS
SELECT S_ID, NAME
FROM   StudentDetails
WHERE  NAME IS NOT NULL
WITH CHECK OPTION;

What the view does: it selects only S_ID and NAME, and only for rows where NAME is not null. The WITH CHECK OPTION means that any INSERT or UPDATE through this view must also satisfy NAME IS NOT NULL, or the statement fails.

The statement the source shows as invalid:

INSERT INTO SampleView(S_ID)
VALUES(6);

Why it fails: this INSERT supplies only S_ID. It does not supply a NAME, and the source's note explains the consequence: the default value of the NAME column is null. So the new row would have NAME = NULL, which violates the view's WHERE NAME IS NOT NULL condition. Because the view was created WITH CHECK OPTION, the DBMS refuses the insert and returns an error.

The key point to state in an exam

The view is updatable — the source says so explicitly: “though the View is updatable but then also the below query for this View is not valid”. The reason the insert fails is not that the view is read-only, but that the new row would fall outside the view's own condition. WITH CHECK OPTION converts that situation from a silent anomaly into a refused statement.

32.2 Five-Mark Questions

Q1. Explain the difference between a super key, a candidate key and a primary key, with an example.

Answer. A super key is any set of attributes that identifies each tuple uniquely; it may contain attributes that are not needed for uniqueness. A candidate key is a minimal super key: removing any attribute destroys uniqueness. The primary key is the candidate key the designer chooses to implement.

Consider Student ( roll, name, sex, age, address, class, section ), assuming names are unique. The whole tuple is a super key. ( class, section, roll, sex ) is also a super key, but it is not minimal because sex is removable. ( class, section, roll ) and ( name, address ) are candidate keys. If the designer implements ( class, section, roll ) as the primary key, then ( name, address ) becomes the alternate key. A table may have several candidate keys but exactly one primary key.

Q2. Explain the three anomalies that normalization removes, with an example of each.

Answer. Take an unnormalized relation ( Stu_ID, Stu_Name, Dept, Course, Instructor ) with key (Stu_ID, Course).

Update anomaly. A student's department is stored once per course the student takes. Updating the department in one row leaves the other row unchanged, so the database now contains two different answers to the same question — an inconsistent state.

Insertion anomaly. A new course with its instructor cannot be recorded until a student enrols in it, because the primary key requires a Stu_ID. Recording the fact would need an invented or NULL key value.

Deletion anomaly. If one student is the only person taking a course, deleting that student also deletes the fact that the course is taught by that instructor — information that belonged to the course, not the student.

All three arise from the same cause: facts about different things (students, courses, instructors) sharing one relation. Normalization separates them.

Q3. State and explain the five conditions required to update a view.

Answer. A view is updatable only if all five hold:

  1. The defining SELECT must not contain GROUP BY or ORDER BY. Grouped rows do not correspond to base rows, and ordering is a presentation concern.
  2. It must not contain DISTINCT. Eliminating duplicates loses the identity of the underlying rows.
  3. All view values must be NOT NULL, so that each view row is a complete, insertable row.
  4. The view must not be built from nested or complex queries, which hide the mapping to the base table.
  5. The view must be built from a single table. A view over multiple tables (a join) has no single row to update.

The five conditions share one underlying requirement: the DBMS must be able to map each view row back to exactly one base-table row, and each view column back to a base column.

Q4. Explain the six control measures of database security and the threat each addresses.

Answer. The source lists six:

  1. Authentication — confirms that a user is who they claim to be, using passwords or biometrics such as retina and fingerprints; addresses impersonation and unauthorized entry.
  2. Access control — creates user accounts and restricts access so that sensitive data is reachable only by authorized users; the DBMS must also track all operations a user performs during the login. Addresses reading or modifying data beyond one's privilege.
  3. Inference control — the countermeasure to the statistical-database problem; prevents indirect disclosure through inference channels. Inferences are identity disclosure or attribute disclosure.
  4. Flow control — prevents information from flowing to unauthorized users; the illicit pathways are called covert channels.
  5. Statistical database security — permits summary information such as the number of employees, but not the confidential individual values.
  6. Encryption — encodes sensitive data such as credit card and OTP numbers, protecting it when the storage medium itself is lost.

Each control addresses a different threat, which is why all six are needed.

Q5. Explain the three forms of LOOP statement in PL/SQL, and state how many times each body can execute.

Answer.

  1. Basic LOOP. Statements are enclosed between LOOP and END LOOP with no built-in condition; termination requires EXIT or EXIT WHEN inside the body. Because there is no test before the first execution, the body runs at least once.
  2. WHILE-LOOP. WHILE condition LOOP … END LOOP;. The condition is evaluated before each iteration; if it is false or null the loop is bypassed. The body may therefore run zero times, and the number of iterations is unknown until the loop completes.
  3. FOR-LOOP. FOR counter IN [REVERSE] lower..higher LOOP … END LOOP;. The range is evaluated once when the loop is first entered and is never re-evaluated. The body runs once per integer in the range — exactly once if the bounds are equal, and zero times only if the range is empty. The counter can be read but not assigned.

Q6. Explain the restrictions on the GOTO statement in PL/SQL.

Answer. A GOTO branches unconditionally to a label, which must be unique within its scope and must precede an executable statement or a PL/SQL block. The restrictions are:

  • It cannot branch into an IF statement, CASE statement, LOOP statement or sub-block.
  • It cannot branch from one IF statement clause to another, or from one CASE WHEN clause to another.
  • It cannot branch from an outer block into a sub-block (an inner BEGIN-END block).
  • It cannot branch out of a subprogram. To end a subprogram early, use RETURN, or have GOTO branch to a place just before the end of the subprogram.
  • It cannot branch from an exception handler back into the current BEGIN-END block — but it can branch from an exception handler into an enclosing block.

The source adds that GOTO is seldom needed and should be used sparingly, because overuse makes control flow hard to follow; an exception handler is usually preferable to branching out of deeply nested structure.

32.3 Ten-Mark / Descriptive Questions

Q1. Explain the complete normalization ladder from 1NF to 5NF, stating the rule and the problem addressed at each level. Illustrate with the Student_Project and Employee examples.

Answer structure. Define normalization and its purpose. Then, for each form, state the rule, name the dependency removed, and give the source's example:

  • 1NF — atomic values only. Example: the EMPLOYEE table whose EMP_PHONE column holds several numbers in one cell; splitting them into separate rows reaches 1NF and makes the key composite.
  • 2NF — no partial dependency. Example: Student_Project ( Stu_ID, Proj_ID, Stu_Name, Proj_Name ), where Stu_Name depends only on Stu_ID and Proj_Name only on Proj_ID. Decomposing into a Student relation and a Project relation removes the partial dependencies; a junction relation preserves the many-to-many fact.
  • 3NF — no transitive dependency. Example: Employee ( Emp_ID, Emp_Name, Emp_Zip, Emp_State, Emp_City, Emp_District ), where Emp_Zip determines the location attributes. Splitting into Employee_ID and Employee_Zip stores each location fact once.
  • BCNF — every determinant a super key. Example: the Employee relation with candidate key {Emp_ID, Emp_Dept}, where Emp_ID → Emp_Nationality and Emp_Dept → Dept_Type, No_of_Employees have determinants that are only part of the key. Three relations — Employee_Nationality, Employee_Department and Employee_ID_Dept — make every determinant a key.
  • 4NF — no multivalued dependency. Example: Students ( Stud_ID, Stud_Course, Stud_Hobby ), where course and hobby are independent facts, producing a cross product. Splitting into StudentCourse and StudentHobby removes it.
  • 5NF — every join dependency implied by the candidate keys. Example: the agent/company/product table, where a tuple-formation rule makes the join dependency real; the source notes that detecting such dependencies is very hard, so 5NF is largely of academic interest.

Conclude with the cumulative nature of the ladder and the note that 3NF is usually sufficient in practice, with denormalization applied afterwards only when measurement justifies it.

Q2. Discuss database security in full: definition, importance, the levels of security, threats, and the control measures.

Answer structure.

  1. Definition and scope. Protection from malicious attempts to steal or modify data; formally the array of controls, tools and procedures safeguarding confidentiality, integrity and accessibility. Security must cover the data, the DBMS, associated applications, the physical/virtual server and its hardware, and the computing/network infrastructure.
  2. Importance. Loss of intellectual property, damage to brand reputation, loss of business continuity, and the cost of investigation, repair and customer notification.
  3. Threats and the three losses. Loss of integrity (improper modification, leading to inaccuracy, fraud or erroneous decisions); loss of availability (objects withheld from legitimate users); loss of confidentiality (unauthorized disclosure, from violation of the Data Privacy Act to jeopardised national security).
  4. Levels. Human, network/user interface, database application program, database system, operating system and physical. Physical security uses lock-and-key, disaster protection and backup; OS security is critical against viruses and worms.
  5. Network and human level. Eavesdropping, masquerading and person-in-the-middle attacks, handled by https://; passwords fail because they are guessable and shared; smartcards require the card plus a PIN.
  6. Control measures. Authentication, access control, inference control, flow control, statistical database security and encryption, each tied to the threat it addresses.
  7. DBA. The central authority: grants privileges, classifies users and data, and holds the superuser account with account creation, privilege granting, privilege revocation and security level assignment.

/

Answer. The THEN keyword is missing. The correct form is:

   IF a > 5 THEN

   END IF;
Q2 — find the error 
DECLARE
   n NUMBER := 0;
BEGIN
   WHILE n < 5 LOOP
      DBMS_OUTPUT.PUT_LINE(n);
   END LOOP;
END;
/

Answer. The loop is infinite. Nothing inside the body changes n, so the condition n < 5 remains true forever. The source states the rule directly: a statement inside the loop must change the value of the condition. Adding n := n + 1; inside the body fixes it.

Q3 — find the error 
BEGIN
   FOR i IN 1..3 LOOP
      DBMS_OUTPUT.PUT_LINE(i);
      i := i + 1;
   END LOOP;
END;
/

Answer. The loop counter cannot be assigned inside a FOR loop. The counter may be referenced like a constant but not modified, because the loop itself controls it. The statement i := i + 1; must be removed.

Q4 — find the error 
DECLARE
   CURSOR c IS SELECT id, name FROM customers;

      EXIT WHEN c%NOTFOUND;
   END LOOP;

/

Answer. Three faults. First, the cursor is never OPENed, so the FETCH raises ORA-01001: invalid cursor. Second, the variables v_id and v_name are never declared. Third, the cursor is never CLOSEd. The corrected skeleton is:

   LOOP
      FETCH c INTO v_id, v_name;
      EXIT WHEN c%NOTFOUND;

/
Q5 — find the error 
CREATE VIEW HighMarks AS

32.6 Normalization Problems with Step-by-Step Solutions

Problem 1 — drive a relation to 3NF

Relation. R ( Stu_ID, Stu_Name, Zip, City, Course ), with Stu_ID → Stu_Name, Zip, Zip → City, and the key being ( Stu_ID, Course ).

Step 1 — is it in 1NF? Assume all values are atomic, so yes.

Step 2 — is it in 2NF? The key is (Stu_ID, Course). Test each non-prime attribute:

AttributeDetermined byWhole key needed?
Stu_NameStu_IDNo — partial
ZipStu_IDNo — partial
CityZipNo — not even on the key

Not in 2NF. Fix: split along the partial dependencies into Student ( Stu_ID, Stu_Name, Zip ) and Enrolment ( Stu_ID, Course ).

Step 3 — is the result in 3NF? Student has key Stu_ID, and the dependency Stu_ID → Zip is fine. But where does City live? If City is placed in Student, then Stu_ID → Zip → City is a transitive dependency, so Student would not be in 3NF. Fix: move City into a relation keyed by Zip: ZipInfo ( Zip, City ).

Final schema (all in 3NF):

Student   ( Stu_ID, Stu_Name, Zip )     key Stu_ID
ZipInfo   ( Zip, City )                 key Zip
Enrolment ( Stu_ID, Course )            key (Stu_ID, Course)

Check the decomposition is lossless. Student ∩ ZipInfo = { Zip }, and Zip is a super key of ZipInfo, so the join Student ⨝ ZipInfo is lossless. Enrolment shares Stu_ID with Student, and Stu_ID is a super key of Student, so that join is lossless too.

Problem 2 — drive a relation to BCNF

Relation. R ( Emp_ID, Emp_Nationality, Emp_Dept, Dept_Type, No_of_Employees ) — the source's own BCNF example.

Step 1 — find the candidate key. Neither Emp_ID alone nor Emp_Dept alone determines everything, so the candidate key is { Emp_ID, Emp_Dept }.

Step 2 — list the dependencies.

Emp_ID   → Emp_Nationality
Emp_Dept → Dept_Type, No_of_Employees

Step 3 — test BCNF. For each dependency, is the determinant a super key?

DependencyDeterminantSuper key?
Emp_ID → Emp_NationalityEmp_IDNo — only part of the key
Emp_Dept → Dept_Type, No_of_EmployeesEmp_DeptNo — only part of the key

Not in BCNF. Step 4 — fix: give each non-super-key determinant its own relation, and keep a junction for the original relationship.

Employee_Nationality ( Emp_ID, Emp_Nationality )              key Emp_ID
Employee_Department  ( Emp_Dept, Dept_Type, No_of_Employees ) key Emp_Dept
Employee_ID_Dept     ( Emp_ID, Emp_Dept )                     key (Emp_ID, Emp_Dept)

Step 5 — verify. In each relation, every determinant is now the key, hence a super key. All three are in BCNF. The junction relation has no non-key attributes, so it is trivially in BCNF.

Problem 3 — drive a relation to 4NF

Relation. Students ( Stud_ID, Stud_Course, Stud_Hobby ) — the source's own 4NF example. Suppose student S1 takes DBMS and OS, and has hobbies Cricket and Music.

Step 1 — is there a multivalued dependency? For a single Stud_ID, the set of courses and the set of hobbies are independent. So Stud_ID →→ Stud_Course and Stud_ID →→ Stud_Hobby.

Step 2 — confirm the symptom. The table holds the cross product: two courses × two hobbies = four rows. Every course is paired with every hobby, which is redundancy, not information.

Step 3 — fix. Split into one relation per multi-valued fact:

StudentCourse ( Stud_ID, Stud_Course )   key (Stud_ID, Stud_Course)
StudentHobby  ( Stud_ID, Stud_Hobby )    key (Stud_ID, Stud_Hobby)

Step 4 — verify. Each relation is in BCNF (the whole key determines the non-key attribute), and neither contains a multivalued dependency, so both are in 4NF. The two relations together carry exactly the same information as the original, with the cross-product rows removed.

Problem 4 — test a decomposition for losslessness

Relation. R ( A, B, C, D ) with dependencies A → B and C → D, key ( A, C ).

Question. Is the decomposition into R1 ( A, B ) and R2 ( A, C, D ) lossless?

Test. R1 ∩ R2 = { A }. Is A a super key of R1? Yes — A → B and R1 = { A, B }. So the decomposition is lossless.

Question. Is the alternative decomposition into R1 ( A, B ) and R2 ( C, D ) lossless?

Test. R1 ∩ R2 = ∅. The empty set is a super key of neither relation (it determines nothing). So this decomposition is lossy — joining the pieces would produce the full cross product A × B × C × D, which contains spurious tuples. The key ( A, C ) would be lost entirely.

The method to reuse in an examination
  1. Write down the functional dependencies. Nothing else is possible without them.
  2. Find the candidate key by computing closures.
  3. Test 2NF: does any non-prime attribute depend on part of a composite key?
  4. Test 3NF: does any non-prime attribute depend on another non-prime attribute?
  5. Test BCNF: is any determinant not a super key?
  6. Test 4NF: are two independent multi-valued facts in one table?
  7. Verify losslessness at the end using the R1 ∩ R2 super-key test.

34. Viva Questions

Part 8  •  short spoken answers to the questions examiners actually ask

Viva answers should be short, start with the key term, and stop. Each answer below is written to be spoken in one or two sentences.

Keys

1. What is a key?

An attribute or set of attributes that helps identify a row in a relation and establish relationships between tables.

2. Difference between a super key and a candidate key?

A super key identifies uniquely but may contain redundant attributes; a candidate key is a minimal super key, so no attribute can be removed.

3. Can a foreign key be NULL?

Yes. A foreign key may take the NULL value, meaning no related row is currently assigned.

4. Can a foreign key be non-unique?

Yes — in fact a foreign key is usually not unique, because many rows in the referencing table normally point to the same master row.

5. What is the difference between a composite key and a compound key?

A composite key is a primary key of two or more attributes; a compound key is a composite key in which every part is itself a foreign key.

6. What is a prime attribute?

An attribute that appears in some candidate key; attributes in no candidate key are non-prime.

Dependencies and normalization

7. What does X → Y mean?

Any two tuples that agree on X must also agree on Y — X determines Y.

8. State Armstrong's three axioms.

Reflexivity: if Y ⊆ X then X → Y. Augmentation: if X → Y then XZ → YZ. Transitivity: if X → Y and Y → Z then X → Z.

9. Can you split the left-hand side of a dependency?

No. From AB → C you cannot infer A → C. Decomposition applies to the right-hand side only.

10. Why does normalization matter?

It removes redundancy and therefore the update, insertion and deletion anomalies that redundancy causes.

11. What is a partial dependency?

A non-prime attribute that depends on only part of a composite candidate key; 2NF removes it.

12. What is a transitive dependency?

A chain X → Y → Z where Y does not determine X; 3NF removes it.

13. Difference between 3NF and BCNF?

3NF permits X → A when A is a prime attribute even if X is not a super key; BCNF requires every determinant of a non-trivial dependency to be a super key.

14. What is a multivalued dependency?

When two independent multi-valued facts about the same determinant share one table, producing a cross product; 4NF removes it.

15. Why is 5NF largely of academic interest?

Because join dependencies are very difficult to detect in practice, as the source itself notes.

16. What is a lossless decomposition?

One whose relations, joined back, reproduce the original relation exactly, with no rows lost and no spurious rows created.

17. State the lossless-join test.

The common attributes of the two relations must form a super key of at least one of them.

18. Does denormalization mean abandoning normalization?

No. It is an optimization applied after normalization, adding redundancy deliberately to avoid costly joins.

Security

19. What is database security?

Protection from malicious attempts to steal or modify data — the array of controls, tools and procedures safeguarding confidentiality, integrity and accessibility.

20. Name the three properties security must preserve.

Confidentiality, integrity and availability.

21. Difference between authentication and authorization?

Authentication proves who the user is; authorization decides what that user may do. Authentication happens first.

22. Name the three access-control models.

Discretionary (owner-controlled, using ACLs), mandatory (labels and clearance levels), and role-based (permissions attached to roles).

23. What is inference control?

A control that prevents a user from deducing sensitive information indirectly, by combining legitimate answers.

24. What is a covert channel?

A pathway by which information flows implicitly in a way that violates the privacy policy of the organization.

25. What is the main issue with encryption?

Key management — the key must be available at startup but must not be stored with the data, and losing it makes the data unreadable.

26. What is a threat?

Any intentional or accidental event that may adversely affect the system.

PL/SQL control structures

27. Name the three categories of control structure.

Conditional, iterative and sequential.

28. Difference between EXIT and EXIT WHEN?

EXIT leaves the loop unconditionally; EXIT WHEN evaluates a condition first and leaves only if it is true.

29. Can a WHILE loop body execute zero times?

Yes. The condition is tested at the top, so if it is false or null on entry the loop is bypassed.

30. Can a FOR loop body execute zero times?

Not for a normal ascending range — but if the range is empty (lower bound greater than higher bound without REVERSE) the body does not execute.

31. What happens if the FOR loop bounds are equal?

The body executes exactly once.

32. What does EXIT outer do in nested loops?

It exits every enclosing loop up to and including the labelled loop named outer.

33. What does the NULL statement do?

Nothing — it is a no-op, used to make it clear that a branch is deliberately empty.

34. Name two GOTO restrictions.

It cannot branch into an IF, CASE, LOOP or sub-block; and it cannot branch out of a subprogram. (Also: no jumping between IF clauses or CASE WHEN clauses; and from an exception handler it may jump out to an enclosing block but not back into the current block.)

Cursors and views

35. What is a cursor?

A pointer to the result set of a SQL query against database tables.

36. What is the active set?

The rows in the context area that meet the condition; its size equals the number of such rows.

37. Name the four explicit cursor steps.

Declare, open, fetch, close.

38. Why is SQL%ISOPEN always FALSE?

Because Oracle closes the implicit cursor automatically after executing the associated statement.

39. Why must EXIT WHEN come immediately after FETCH?

Because the cursor attribute reflects the most recent fetch; testing it immediately prevents the loop from processing a row that was not retrieved.

40. What is a view?

A specific representation of data from one or more tables, storing only the query and not the data.

41. What is a base table?

A table referred to in the definition of a view — the table that actually stores the data.

42. How many columns can a view have?

A maximum of 1000, as in tables.

43. Name the five conditions for updating a view.

No GROUP BY or ORDER BY; no DISTINCT; all NOT NULL values; not built from nested or complex queries; and built from a single table.

44. What does WITH CHECK OPTION do?

It makes the view's WHERE condition a constraint on writes: an INSERT or UPDATE that would not satisfy it returns an error.

45. Does dropping a view delete data?

No — it removes only the view definition, because the view stored no data of its own.

Common mistakes and examination traps

The ten most costly errors
  1. Writing “authentication controls what a user may access”. It is authorization that does that.
  2. Saying a table can have two primary keys. It can have many candidate keys, one primary key.
  3. Reversing the direction of a dependency and reading X → Y as “X depends on Y”.
  4. Splitting the left side of a dependency (from AB → C inferring A → C). Decomposition is right-side only.
  5. Treating 4NF as a replacement for BCNF. 4NF includes BCNF.
  6. Claiming a WHILE loop always runs at least once. Its condition is at the top.
  7. Writing ELSE IF instead of ELSIF.
  8. Testing %NOTFOUND before the first FETCH in a cursor loop.
  9. Forgetting that an unclosed cursor holds server memory.
  10. Believing denormalization means skipping normalization. It is applied after it.

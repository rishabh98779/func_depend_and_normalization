6. Normalization Fundamentals and First Normal Form

Part 3  •  why we decompose at all

Before learning six normal forms, it helps to know exactly what disease they are treating. The disease is redundancy: the same fact stored in more than one place. Redundancy is not merely wasteful; it is the direct cause of three specific failures called anomalies. Normalization is the systematic removal of redundancy by decomposition, and each normal form removes one more kind of redundancy.

6.1 What Normalization Is

Definition (source)

Normalization is a process of designing a consistent database by minimising redundancy and ensuring data integrity through decomposition which is lossless. It is a systematic, step-by-step decomposition of complex records into simple records.

The source lists several characterisations, all of which are worth knowing because exam questions often ask for two or three of them.

Table 6.1 — How the source describes normalization.

Features of normalization (source list)

  • It avoids data redundancy.
  • It is a formal process of developing data structures.
  • It promotes data integrity.
  • It ensures data dependencies make sense — that is, data is logically stored.
  • It eliminates undesirable characteristics.

How normalization works, in the source's words

Normalization designs the schema by modifying the existing schema, reducing both redundancy and dependency of the data. Unwanted duplication is removed along with the anomalies. In an insert anomaly, values such as NULL are forced where they should not be; in an update anomaly, data cannot be updated correctly because the same value occurs multiple times in a column; in a delete anomaly, deleting one record removes facts that belong to other records. The aim is therefore to remove redundant data and store only related data in each table, which decreases database size and makes the data logically stored.

6.2 The Three Anomalies

The source defines the three anomalies and, crucially, the definition of each is best understood on a single example. Use this one table throughout the section.

Table 6.2 — An unnormalized relation used to demonstrate all three anomalies. The primary key is (Stu_ID, Course).
Stu_IDStu_NameDeptCourseInstructor

101AnanyaCSEOSDr. Verma

The three anomalies

Update anomaly. If data items are scattered and not linked properly, updating one fact leaves copies elsewhere unchanged. Here “Ananya's department is CSE” appears twice; changing it in one row and not the other leaves the database inconsistent.

Insertion anomaly. Data cannot be inserted because some other, unrelated fact is missing. Here we cannot record that a new course “Networks” is taught by Dr. Nair until at least one student enrols, because the primary key requires a Stu_ID — and we cannot invent one.

Deletion anomaly. Deleting a record removes facts that belong to other records. If Meera is the only student taking Signals, deleting Meera also deletes the fact that Dr. Rao teaches Signals.

6.3 The Ladder of Normal Forms

The source lists six normal forms in order. Each is a stricter condition than the one before it, and each removes one more class of redundancy.

6.4 First Normal Form (1NF)

Definition

A relation is in First Normal Form if every attribute contains an atomic value. An attribute of a table cannot hold multiple values; it must hold only single-valued attributes. 1NF therefore disallows multi-valued attributes, composite attributes, and their combinations.

The source gives a second, equivalent statement that is worth remembering: 1NF is defined in the definition of relations themselves — all attributes in a relation must have atomic domains, and the values in an atomic domain are indivisible units. Each attribute must contain only a single value from its predefined domain.

Source Example 1 — the EMPLOYEE table

The source's first example is an EMPLOYEE relation that is not in 1NF because EMP_PHONE is multi-valued: one employee row lists several phone numbers in a single cell.

Explanation — the price of 1NF

Notice what happened: the fix introduced repetition of Emp_ID and Emp_Name. That repetition is precisely what 2NF will now attack. This is the pattern of the whole ladder — each normal form removes one kind of redundancy, and sometimes exposes the next kind.

Source Example 2 — a course-enrolment relation

The source's second example is a relation in which a single student cell or course cell holds several values. Rearranging it so that each attribute holds a single value from its domain converts it to 1NF, exactly as above. The same principle applies: one cell, one value.

Common mistake

Believing that 1NF is about the number of columns. It is not. 1NF is about the contents of one cell. A table with 200 columns is perfectly capable of being in 1NF, provided every cell holds exactly one indivisible value. Equally, a two-column table can violate 1NF if a cell contains a list.

Quick test for 1NF

Ask of every column: “Can this cell ever need to hold two values?” A comma-separated list, a set of tags, an array, or a repeating group in a cell all mean the answer is yes, and the relation is not in 1NF. The fix is always the same: move the repeated values into their own rows.

Chapter summary

Summary — Chapter 6
  • Normalization is lossless decomposition to remove redundancy and anomalies; it was introduced by E. F. Codd and is also called canonical synthesis.
  • The three anomalies are update, insertion and deletion; all three come from unrelated facts sharing one table.
  • 1NF requires atomic values: no multi-valued attributes, no composite attributes, no repeating groups inside a cell.
  • The ladder runs 1NF → 2NF → 3NF → BCNF → 4NF → 5NF and is cumulative.

7. Second Normal Form (2NF)

Part 3  •  removing partial dependencies

2NF is the first form that depends on which attributes are prime. Before stating the rule, the source defines the two terms the rule needs.

7.1 Prime and Non-Prime Attributes

Definitions (source)

Prime attribute. An attribute that is part of a candidate key.

Non-prime attribute. An attribute that is not part of any candidate key.

The source's note in the keys chapter says the same thing in one line: those attributes which appear in some candidate key are called prime attributes. Note that a prime attribute must be part of some candidate key — not necessarily of the primary key you happened to choose.

7.2 The 2NF Rule: Full Functional Dependency

Definition

If we follow Second Normal Form, then every non-prime attribute must be fully functionally dependent on the primary key. That is: if X → A holds, there must be no proper subset Y of X for which Y → A also holds.

In the source's formulation, a table is in 2NF when two conditions are met:

  1. The table is in the first normal form.
  2. The primary key of the table is composed of exactly one column.
Explanation — the two statements are the same rule

The second condition looks like a different rule, and students often wonder why a single-column key automatically gives 2NF. The reason is that a single-column key has no proper subset other than the empty set, so a partial dependency is impossible. Conversely, when the key has two or more columns, a non-prime attribute might depend on only one of them — and that is exactly the violation. So “no proper subset determines the attribute” and “the key is a single column” describe the same requirement from two angles.

7.3 Partial Dependency and How to Remove It

Definition

A partial dependency exists when a non-prime attribute depends on part of a composite candidate key rather than on the whole key.

The source's Student_Project relation is the canonical example. Its prime key attributes are Stu_ID and Proj_ID. The rule says the non-key attributes Stu_Name and Proj_Name must depend on both, not on either individually. But Stu_Name can be identified by Stu_ID alone, and Proj_Name by Proj_ID alone. Those are partial dependencies, and 2NF forbids them.

The two tables above remove the redundancy, but they also remove the fact that S1 works on P1. 7.4 Worked 2NF Example

The source's enrolment table

The source's second example is a student-enrolment table. Its first column is the student name, its second the course code.

Neither column is unique — “Rahul” appears in rows 1 and 3, “CS101” appears in rows 2 and 4 — but the pair ( Student Name, Course Code ) is unique, because a student cannot enrol in the same course more than once. So the pair is the primary key.

As per the 2NF definition this table is not in 2NF. In this particular table both columns are prime, so there is no non-prime attribute to violate the rule literally; the source's real point is the structural one: a two-column key is a table in which partial dependencies can arise, and the standard treatment is to separate the entity from the relationship. The source does exactly that, by introducing an enrolment number as a single-column key.

The source's closing remark is exactly right: these two tables together provide the exact same information as the original table. That is the definition of a lossless decomposition, formalised in Chapter 12.

Explanation — the shape of a 2NF fix

Every 2NF decomposition has the same shape. You identify a composite key; you notice that some non-prime attribute depends on only one part of it; you move that attribute into a new table whose key is that one part. The junction table keeps only the two key parts, and it is what preserves the original many-to-many fact.

Quick test for 2NF

Look at the primary key. If it has one column, the relation is automatically in 2NF (given 1NF). If it has two or more columns, check every non-prime attribute: does it need the whole key, or would one part of the key do? If one part would do, the relation is not in 2NF.

Chapter summary

Summary — Chapter 7
  • A prime attribute belongs to some candidate key; a non-prime attribute belongs to none.
  • 2NF requires 1NF plus the rule that every non-prime attribute is fully functionally dependent on the key — no proper subset of the key determines it.
  • A partial dependency is a non-prime attribute depending on part of a composite key.
  • The fix is to split the relation so each non-prime attribute sits with the smallest key that determines it, keeping a junction relation to preserve the original relationship.

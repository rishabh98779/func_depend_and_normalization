27. Cursors: Concept and Implicit Cursors

Part 6  •  working with a result set one row at a time

A cursor exists to solve a mismatch. SQL is set-oriented: a query returns a whole set of rows at once. A procedural program is row-oriented: it does one thing at a time. Something must bridge the two, and in PL/SQL that something is the cursor.

27.1 What a Cursor Is

Definition (source)

A PL/SQL cursor is a pointer that points to the result set of an SQL query against database tables.

The source explains why it is needed: when you work with an Oracle database, you work with a complete set of rows returned from a SELECT statement. However, the application in some cases cannot work effectively with the entire result set. Therefore the database server needs to provide a mechanism for the application to work with one row, or a subset of the result set, at a time. Oracle created the PL/SQL cursor to provide these extensions.

The single word to hold on to is pointer. A cursor is not the data; it is a position within the data. Each fetch moves the pointer forward one row, and the program acts on whatever row the pointer currently indicates.

27.2 The Context Area and the Active Set

The source's explanation

Oracle has dedicated memory locations for executing SQL statements, and holds that processed information — for example, the total number of rows updated. A cursor in PL/SQL gives a name and acts as a pointer to the area of work called a context area, and then uses its information. It keeps the number of rows processed by the SQL statement. These rows are called the active set. The size of the active set is equal to the count of the rows that meet the condition.

Table 27.1 — The four terms, defined.
TermMeaning
CursorA pointer to the result set of a SQL query against database tables

27.3 Implicit Cursors

Definition (source)

Implicit cursors are automatically created by Oracle whenever an SQL statement is executed, when there is no explicit cursor for the statement. Programmers cannot control the implicit cursors and the information in them.

Whenever a DML statement (INSERT, UPDATE and DELETE) is issued, an implicit cursor is associated with that statement. For INSERT operations, the cursor holds the data that needs to be inserted. For UPDATE and DELETE operations, the cursor identifies the rows that would be affected.

Three consequences follow, and they are worth stating separately because exam questions often probe them:

  1. You do not declare an implicit cursor. Oracle creates it for you whenever you run a DML statement or a SELECT … INTO.
  2. You do not open or close it. Oracle manages its whole life cycle, and closes it automatically after executing the associated statement.
  3. You can read its attributes. This is the part that makes implicit cursors useful. The attributes tell you what the statement just did.

27.4 Implicit Cursor Attributes

The SQL cursor (source)

In PL/SQL you can refer to the most recent implicit cursor as the SQL cursor, which always has attributes such as %FOUND, %ISOPEN, %NOTFOUND and %ROWCOUNT. The SQL cursor has additional attributes, %BULK_ROWCOUNT and %BULK_EXCEPTIONS, designed for use with the FORALL statement.

Any SQL cursor attribute is accessed as sql%attribute_name.

Table 27.2 — The four most-used implicit cursor attributes, in the source's words.
AttributeReturns TRUE / value when…
SQL%FOUNDReturns TRUE if an INSERT, UPDATE or DELETE statement affected one or more rows, or a SELECT INTO statement returned one or more rows. Otherwise it returns FALSE.
SQL%NOTFOUNDThe logical opposite of %FOUND. Returns TRUE if an INSERT, UPDATE or DELETE statement affected no rows, or a SELECT INTO returned no rows. Otherwise it returns FALSE.
SQL%ISOPENAlways returns FALSE for implicit cursors, because Oracle closes the SQL cursor automatically after executing its associated SQL statement.
SQL%ROWCOUNTReturns the number of rows affected by an INSERT, UPDATE or DELETE statement, or returned by a SELECT INTO statement.

27.5 Worked Implicit Cursor Program

Program — using SQL%ROWCOUNT (source)

Problem: increase every customer's salary by 500, and report how many customers were affected.

The source uses this CUSTOMERS table throughout the chapter:

Table 27.3 — The CUSTOMERS table used in the source's cursor examples.
IDNAMEAGEADDRESSSALARY
1Ramesh32Ahmedabad2000
2Khilan25Delhi1500
3kaushik23Kota2000
4Chaitali25Mumbai6500
5Hardik27Bhopal8500

DECLARE
   total_rows number(2);
BEGIN
   UPDATE customers
   SET    salary = salary + 500;

   IF sql%notfound THEN
      dbms_output.put_line('no customers selected');
   ELSIF sql%found THEN
      total_rows := sql%rowcount;
      dbms_output.put_line( total_rows || ' customers selected ');
   END IF;
END;
/

Logic: the UPDATE has no WHERE clause, so it affects every row. Oracle associates an implicit cursor with it. The block then tests sql%notfound: if no rows were affected, it prints a “none” message. Otherwise sql%found is true, so it copies sql%rowcount — the number of rows the UPDATE affected — into total_rows and prints it.

PL/SQL procedure successfully completed.

The source adds: if you check the records in the customers table, you will find that the rows have been updated. Every salary is now 500 higher than in Table 27.3.

Explanation — what the attributes prove here

Notice what the program demonstrates. It never names the implicit cursor, never opens it and never closes it — yet it still learns a fact about what just happened. That is the whole point of implicit cursor attributes: they are the DBMS telling you the outcome of the statement it just executed for you.

28. Explicit Cursors and Cursor Loops

Part 6  •  declare, open, fetch, close — and terminate correctly

An implicit cursor is convenient but opaque: you can read its attributes, but you cannot control it. When a program needs real control over a multi-row query — reading rows one at a time, deciding when to stop — it needs an explicit cursor.

28.1 Declaring, Opening, Fetching and Closing

Definition (source)

Explicit cursors are programmer-defined cursors for gaining more control over the context area. An explicit cursor should be defined in the declaration section of the PL/SQL block. It is created on a SELECT statement which returns more than one row.

CURSOR cursor_name IS select_statement;

The source lists the four steps of working with an explicit cursor, and the order matters:

  1. Declaring the cursor, for initialising the memory.
  2. Opening the cursor, for allocating the memory.
  3. Fetching the cursor, for retrieving the data.
  4. Closing the cursor, to release the allocated memory.
Table 28.1 — The four steps, with the source's syntax and explanation for each.
StepSyntax (source)What it does (source)
DeclareCURSOR c_customers IS
SELECT id, name, address FROM customers;		Defines the cursor with a name and the associated SELECT statement.
OpenOPEN c_customers;Allocates the memory for the cursor and makes it ready for fetching the rows returned by the SQL statement into it.
FetchFETCH c_customers INTO c_id, c_name, c_addr;Accesses one row at a time.
CloseCLOSE c_customers;Releases the allocated memory.

28.3 Worked Explicit Cursor Program

Program — reading the CUSTOMERS table (source)

Problem: print the id, name and address of every customer.

DECLARE
   c_id    customers.id%type;
   c_name  customer.name%type;
   c_addr  customers.address%type;

   CURSOR c_customers is
      SELECT id, name, address FROM customers;
BEGIN
   OPEN c_customers;
   LOOP
      FETCH c_customers into c_id, c_name, c_addr;
      EXIT WHEN c_customers%notfound;
      dbms_output.put_line(c_id || ' ' || c_name || ' ' || c_addr);
   END LOOP;
   CLOSE c_customers;
END;
/

Structure: the declaration section holds three variables, each typed with %type so that its data type matches the corresponding column automatically, plus the cursor itself. The body opens the cursor, then loops: fetch a row into the three variables, test the cursor's %notfound attribute to decide whether to stop, and if there is a row, print it. After the loop the cursor is closed.

Explanation — why EXIT WHEN comes straight after FETCH

The order inside the loop is not arbitrary. FETCH must run before EXIT WHEN c_customers%notfound because the attribute describes the most recent fetch. Placing the EXIT immediately after the FETCH means the loop stops the moment a fetch finds no row, and never prints an uninitialised row. If the print came first, the final iteration would print stale values from the previous row.

Explanation — the one attribute that differs in meaning

For an implicit cursor %ISOPEN is always FALSE because Oracle has already closed it. For an explicit cursor %ISOPEN is genuinely useful: it is TRUE between OPEN and CLOSE. This is a favourite viva question precisely because the same attribute name behaves differently in the two cases.

28.5 Cursor Errors and Exam Traps

Common mistake 1 — forgetting to open the cursor

Fetching from a cursor that has not been opened raises ORA-01001: invalid cursor. The OPEN statement is what allocates the context area; without it there is nothing to fetch from.

Common mistake 2 — testing %NOTFOUND before the first fetch

Immediately after OPEN, the cursor has not fetched anything, so %FOUND and %NOTFOUND do not yet reflect the data. The reliable pattern — the one the source uses — is FETCH first, then EXIT WHEN c%NOTFOUND. A loop that tests %NOTFOUND before its first fetch may process one row too many or too few.

Common mistake 3 — forgetting to close

An unclosed cursor keeps its context area allocated until the session ends. In a program that opens many cursors, that is a memory leak. CLOSE c_customers; releases the memory, and the source places it after the loop for exactly this reason.

Common mistake 4 — a cursor for a query that returns one row

The source specifies that an explicit cursor “is created on a SELECT Statement which returns more than one row”. If a query is guaranteed to return a single row, SELECT … INTO with an implicit cursor is the simpler and more appropriate tool. Using a cursor loop for a single row works but adds ceremony for no benefit.

The pattern to memorise 
CURSOR c IS SELECT … ;      -- declare (in DECLARE section)
…
OPEN  c;                    -- allocate
LOOP
   FETCH c INTO …;          -- get the next row
   EXIT WHEN c%NOTFOUND;    -- stop when there is none
   … process the row …      -- only reached for a real row
END LOOP;
CLOSE c;                    -- release

Every explicit cursor program in this chapter, and in the source, is a variation on these six lines.

Chapter summary

Summary — Chapter 28
  • Explicit cursors are programmer-defined and declared in the declaration section; they are created on a SELECT that returns more than one row.
  • The four steps are declare (initialise memory), open (allocate memory), fetch (retrieve one row at a time) and close (release memory).
  • A cursor loop fetches, tests %NOTFOUND to decide whether to stop, and processes the row. The EXIT WHEN must come immediately after the FETCH.
  • Explicit cursors are closed by you; implicit cursors are closed by Oracle, which is why SQL%ISOPEN is always FALSE.
  • Common errors: fetching without opening, testing %NOTFOUND before the first fetch, forgetting to close, and using a cursor where a single-row SELECT … INTO would do.

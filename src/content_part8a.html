32.2 Five-Mark Questions

Q1. Explain the difference between a super key, a candidate key and a primary key, with an example.

Answer. A super key is any set of attributes that identifies each tuple uniquely; it may contain attributes that are not needed for uniqueness. A candidate key is a minimal super key: removing any attribute destroys uniqueness. The primary key is the candidate key the designer chooses to implement.

Consider Student ( roll, name, sex, age, address, class, section ), assuming names are unique. The whole tuple is a super key. ( class, section, roll, sex ) is also a super key, but it is not minimal because sex is removable. ( class, section, roll ) and ( name, address ) are candidate keys. If the designer implements ( class, section, roll ) as the primary key, then ( name, address ) becomes the alternate key. A table may have several candidate keys but exactly one primary key.

Q2. Explain the three anomalies that normalization removes, with an example of each.

Answer. Take an unnormalized relation ( Stu_ID, Stu_Name, Dept, Course, Instructor ) with key (Stu_ID, Course).

Update anomaly. A student's department is stored once per course the student takes. Updating the department in one row leaves the other row unchanged, so the database now contains two different answers to the same question — an inconsistent state.

Insertion anomaly. A new course with its instructor cannot be recorded until a student enrols in it, because the primary key requires a Stu_ID. Recording the fact would need an invented or NULL key value.

Deletion anomaly. If one student is the only person taking a course, deleting that student also deletes the fact that the course is taught by that instructor — information that belonged to the course, not the student.

All three arise from the same cause: facts about different things (students, courses, instructors) sharing one relation. Normalization separates them.

Q3. State and explain the five conditions required to update a view.

Answer. A view is updatable only if all five hold:

  1. The defining SELECT must not contain GROUP BY or ORDER BY. Grouped rows do not correspond to base rows, and ordering is a presentation concern.
  2. It must not contain DISTINCT. Eliminating duplicates loses the identity of the underlying rows.
  3. All view values must be NOT NULL, so that each view row is a complete, insertable row.
  4. The view must not be built from nested or complex queries, which hide the mapping to the base table.
  5. The view must be built from a single table. A view over multiple tables (a join) has no single row to update.

The five conditions share one underlying requirement: the DBMS must be able to map each view row back to exactly one base-table row, and each view column back to a base column.

Q4. Explain the six control measures of database security and the threat each addresses.

Answer. The source lists six:

  1. Authentication — confirms that a user is who they claim to be, using passwords or biometrics such as retina and fingerprints; addresses impersonation and unauthorized entry.
  2. Access control — creates user accounts and restricts access so that sensitive data is reachable only by authorized users; the DBMS must also track all operations a user performs during the login. Addresses reading or modifying data beyond one's privilege.
  3. Inference control — the countermeasure to the statistical-database problem; prevents indirect disclosure through inference channels. Inferences are identity disclosure or attribute disclosure.
  4. Flow control — prevents information from flowing to unauthorized users; the illicit pathways are called covert channels.
  5. Statistical database security — permits summary information such as the number of employees, but not the confidential individual values.
  6. Encryption — encodes sensitive data such as credit card and OTP numbers, protecting it when the storage medium itself is lost.

Each control addresses a different threat, which is why all six are needed.

Q5. Explain the three forms of LOOP statement in PL/SQL, and state how many times each body can execute.

Answer.

  1. Basic LOOP. Statements are enclosed between LOOP and END LOOP with no built-in condition; termination requires EXIT or EXIT WHEN inside the body. Because there is no test before the first execution, the body runs at least once.
  2. WHILE-LOOP. WHILE condition LOOP … END LOOP;. The condition is evaluated before each iteration; if it is false or null the loop is bypassed. The body may therefore run zero times, and the number of iterations is unknown until the loop completes.
  3. FOR-LOOP. FOR counter IN [REVERSE] lower..higher LOOP … END LOOP;. The range is evaluated once when the loop is first entered and is never re-evaluated. The body runs once per integer in the range — exactly once if the bounds are equal, and zero times only if the range is empty. The counter can be read but not assigned.

Q6. Explain the restrictions on the GOTO statement in PL/SQL.

Answer. A GOTO branches unconditionally to a label, which must be unique within its scope and must precede an executable statement or a PL/SQL block. The restrictions are:

  • It cannot branch into an IF statement, CASE statement, LOOP statement or sub-block.
  • It cannot branch from one IF statement clause to another, or from one CASE WHEN clause to another.
  • It cannot branch from an outer block into a sub-block (an inner BEGIN-END block).
  • It cannot branch out of a subprogram. To end a subprogram early, use RETURN, or have GOTO branch to a place just before the end of the subprogram.
  • It cannot branch from an exception handler back into the current BEGIN-END block — but it can branch from an exception handler into an enclosing block.

The source adds that GOTO is seldom needed and should be used sparingly, because overuse makes control flow hard to follow; an exception handler is usually preferable to branching out of deeply nested structure.

32.3 Ten-Mark / Descriptive Questions

Q1. Explain the complete normalization ladder from 1NF to 5NF, stating the rule and the problem addressed at each level. Illustrate with the Student_Project and Employee examples.

Answer structure. Define normalization and its purpose. Then, for each form, state the rule, name the dependency removed, and give the source's example:

  • 1NF — atomic values only. Example: the EMPLOYEE table whose EMP_PHONE column holds several numbers in one cell; splitting them into separate rows reaches 1NF and makes the key composite.
  • 2NF — no partial dependency. Example: Student_Project ( Stu_ID, Proj_ID, Stu_Name, Proj_Name ), where Stu_Name depends only on Stu_ID and Proj_Name only on Proj_ID. Decomposing into a Student relation and a Project relation removes the partial dependencies; a junction relation preserves the many-to-many fact.
  • 3NF — no transitive dependency. Example: Employee ( Emp_ID, Emp_Name, Emp_Zip, Emp_State, Emp_City, Emp_District ), where Emp_Zip determines the location attributes. Splitting into Employee_ID and Employee_Zip stores each location fact once.
  • BCNF — every determinant a super key. Example: the Employee relation with candidate key {Emp_ID, Emp_Dept}, where Emp_ID → Emp_Nationality and Emp_Dept → Dept_Type, No_of_Employees have determinants that are only part of the key. Three relations — Employee_Nationality, Employee_Department and Employee_ID_Dept — make every determinant a key.
  • 4NF — no multivalued dependency. Example: Students ( Stud_ID, Stud_Course, Stud_Hobby ), where course and hobby are independent facts, producing a cross product. Splitting into StudentCourse and StudentHobby removes it.
  • 5NF — every join dependency implied by the candidate keys. Example: the agent/company/product table, where a tuple-formation rule makes the join dependency real; the source notes that detecting such dependencies is very hard, so 5NF is largely of academic interest.

Conclude with the cumulative nature of the ladder and the note that 3NF is usually sufficient in practice, with denormalization applied afterwards only when measurement justifies it.

Q2. Discuss database security in full: definition, importance, the levels of security, threats, and the control measures.

Answer structure.

  1. Definition and scope. Protection from malicious attempts to steal or modify data; formally the array of controls, tools and procedures safeguarding confidentiality, integrity and accessibility. Security must cover the data, the DBMS, associated applications, the physical/virtual server and its hardware, and the computing/network infrastructure.
  2. Importance. Loss of intellectual property, damage to brand reputation, loss of business continuity, and the cost of investigation, repair and customer notification.
  3. Threats and the three losses. Loss of integrity (improper modification, leading to inaccuracy, fraud or erroneous decisions); loss of availability (objects withheld from legitimate users); loss of confidentiality (unauthorized disclosure, from violation of the Data Privacy Act to jeopardised national security).
  4. Levels. Human, network/user interface, database application program, database system, operating system and physical. Physical security uses lock-and-key, disaster protection and backup; OS security is critical against viruses and worms.
  5. Network and human level. Eavesdropping, masquerading and person-in-the-middle attacks, handled by https://; passwords fail because they are guessable and shared; smartcards require the card plus a PIN.
  6. Control measures. Authentication, access control, inference control, flow control, statistical database security and encryption, each tied to the threat it addresses.
  7. DBA. The central authority: grants privileges, classifies users and data, and holds the superuser account with account creation, privilege granting, privilege revocation and security level assignment.

Q1 — a basic LOOP with EXIT

Predict the output.

DECLARE
   n NUMBER := 0;
BEGIN
   LOOP
      DBMS_OUTPUT.PUT_LINE ('inside: ' || n);
      n := n + 1;
      IF n > 3 THEN
         EXIT;
      END IF;
   END LOOP;
   DBMS_OUTPUT.PUT_LINE ('outside: ' || n);
END;
/

Reasoning. This is a basic LOOP, so the body runs at least once. n is printed before the increment, and the exit test comes after the increment, so the printed sequence is 0, 1, 2, 3 while the value at exit is 4.

Q2 — a WHILE that never runs

Predict the output.

DECLARE
   total NUMBER := 30000;
BEGIN
   WHILE total <= 25000 LOOP

/

Reasoning. The WHILE condition is tested at the top. total starts at 30000, which is greater than 25000, so the condition is false on the first test and the loop body never executes. This is exactly the case the source describes: the loop is bypassed.

after loop, total = 30000
Q3 — a FOR loop with REVERSE

Predict the output.

BEGIN
   FOR i IN REVERSE 1..4 LOOP
      DBMS_OUTPUT.PUT (i || ' ');
   END LOOP;
   DBMS_OUTPUT.NEW_LINE;
END;
/

Reasoning. REVERSE counts downward from the higher bound to the lower, so the counter takes the values 4, 3, 2, 1. The bounds are still written in ascending order (1..4), as the source requires.

Q4 — CASE with no matching WHEN and no ELSE

What happens?

DECLARE
   grade CHAR(1) := 'E';
BEGIN
   CASE grade
      WHEN 'A' THEN DBMS_OUTPUT.PUT_LINE('Distinction');
      WHEN 'B' THEN DBMS_OUTPUT.PUT_LINE('First class');
      WHEN 'C' THEN DBMS_OUTPUT.PUT_LINE('Second class');
   END CASE;
END;
/

Reasoning. The selector is 'E'. No WHEN matches, and this CASE has no ELSE branch. A CASE statement with no matching branch and no ELSE raises a run-time error (CASE_NOT_FOUND). The correct prediction is therefore an error, not empty output — which is the point of the question.

32.5 Debugging Questions

Q1 — find the error 
DECLARE
   a NUMBER := 10;
BEGIN
   IF a > 5
      DBMS_OUTPUT.PUT_LINE('big');
   END IF;
END;
/

Answer. The THEN keyword is missing. The correct form is:

   IF a > 5 THEN
      DBMS_OUTPUT.PUT_LINE('big');
   END IF;
Q2 — find the error 
DECLARE
   n NUMBER := 0;
BEGIN
   WHILE n < 5 LOOP
      DBMS_OUTPUT.PUT_LINE(n);
   END LOOP;
END;
/

Answer. The loop is infinite. Nothing inside the body changes n, so the condition n < 5 remains true forever. The source states the rule directly: a statement inside the loop must change the value of the condition. Adding n := n + 1; inside the body fixes it.

Q3 — find the error 
BEGIN
   FOR i IN 1..3 LOOP
      DBMS_OUTPUT.PUT_LINE(i);
      i := i + 1;
   END LOOP;
END;
/

Answer. The loop counter cannot be assigned inside a FOR loop. The counter may be referenced like a constant but not modified, because the loop itself controls it. The statement i := i + 1; must be removed.

Q4 — find the error 
DECLARE
   CURSOR c IS SELECT id, name FROM customers;
BEGIN
   LOOP
      FETCH c INTO v_id, v_name;
      EXIT WHEN c%NOTFOUND;
   END LOOP;
END;
/

Answer. Three faults. First, the cursor is never OPENed, so the FETCH raises ORA-01001: invalid cursor. Second, the variables v_id and v_name are never declared. Third, the cursor is never CLOSEd. The corrected skeleton is:

DECLARE
   v_id   customers.id%type;
   v_name customers.name%type;
   CURSOR c IS SELECT id, name FROM customers;
BEGIN
   OPEN c;
   LOOP
      FETCH c INTO v_id, v_name;
      EXIT WHEN c%NOTFOUND;
   END LOOP;
   CLOSE c;
END;
/
Q5 — find the error 
CREATE VIEW HighMarks AS
SELECT StudentDetails.NAME, StudentMarks.MARKS
FROM   StudentDetails, StudentMarks
WHERE  StudentDetails.NAME = StudentMarks.NAME
ORDER BY StudentMarks.MARKS;

INSERT INTO HighMarks(NAME, MARKS) VALUES('Test', 99);

Answer. The INSERT will be refused. The view is built from two tables (it is a join) and it also contains an ORDER BY clause. Two of the five conditions for an updatable view are therefore violated: a view must be created from a single table, and its defining SELECT must not contain ORDER BY. The view is read-only.

Q6 — find the error 
CREATE VIEW SampleView AS
SELECT S_ID, NAME
FROM   StudentDetails
WHERE  NAME IS NOT NULL
WITH CHECK OPTION;

INSERT INTO SampleView(S_ID) VALUES (6);

Answer. This is the source's own example, and it is a deliberate trap. The view is updatable, so the INSERT is attempted — but it supplies no NAME, and the default value of NAME is NULL. The new row would therefore violate the view's WHERE NAME IS NOT NULL condition. Because the view was created WITH CHECK OPTION, the DBMS refuses the insert and returns an error.

32.6 Normalization Problems with Step-by-Step Solutions

Problem 1 — drive a relation to 3NF

Relation. R ( Stu_ID, Stu_Name, Zip, City, Course ), with Stu_ID → Stu_Name, Zip, Zip → City, and the key being ( Stu_ID, Course ).

Step 1 — is it in 1NF? Assume all values are atomic, so yes.

Step 2 — is it in 2NF? The key is (Stu_ID, Course). Test each non-prime attribute:

AttributeDetermined byWhole key needed?
Stu_NameStu_IDNo — partial
ZipStu_IDNo — partial
CityZipNo — not even on the key

Not in 2NF. Fix: split along the partial dependencies into Student ( Stu_ID, Stu_Name, Zip ) and Enrolment ( Stu_ID, Course ).

Step 3 — is the result in 3NF? Student has key Stu_ID, and the dependency Stu_ID → Zip is fine. But where does City live? If City is placed in Student, then Stu_ID → Zip → City is a transitive dependency, so Student would not be in 3NF. Fix: move City into a relation keyed by Zip: ZipInfo ( Zip, City ).

Final schema (all in 3NF):

Student   ( Stu_ID, Stu_Name, Zip )     key Stu_ID
ZipInfo   ( Zip, City )                 key Zip
Enrolment ( Stu_ID, Course )            key (Stu_ID, Course)

Check the decomposition is lossless. Student ∩ ZipInfo = { Zip }, and Zip is a super key of ZipInfo, so the join Student ⨝ ZipInfo is lossless. Enrolment shares Stu_ID with Student, and Stu_ID is a super key of Student, so that join is lossless too.

Problem 2 — drive a relation to BCNF

Relation. R ( Emp_ID, Emp_Nationality, Emp_Dept, Dept_Type, No_of_Employees ) — the source's own BCNF example.

Step 1 — find the candidate key. Neither Emp_ID alone nor Emp_Dept alone determines everything, so the candidate key is { Emp_ID, Emp_Dept }.

Step 2 — list the dependencies.

Emp_ID   → Emp_Nationality
Emp_Dept → Dept_Type, No_of_Employees

Step 3 — test BCNF. For each dependency, is the determinant a super key?

DependencyDeterminantSuper key?
Emp_ID → Emp_NationalityEmp_IDNo — only part of the key
Emp_Dept → Dept_Type, No_of_EmployeesEmp_DeptNo — only part of the key

Not in BCNF. Step 4 — fix: give each non-super-key determinant its own relation, and keep a junction for the original relationship.

Employee_Nationality ( Emp_ID, Emp_Nationality )              key Emp_ID
Employee_Department  ( Emp_Dept, Dept_Type, No_of_Employees ) key Emp_Dept
Employee_ID_Dept     ( Emp_ID, Emp_Dept )                     key (Emp_ID, Emp_Dept)

Step 5 — verify. In each relation, every determinant is now the key, hence a super key. All three are in BCNF. The junction relation has no non-key attributes, so it is trivially in BCNF.

Problem 3 — drive a relation to 4NF

Relation. Students ( Stud_ID, Stud_Course, Stud_Hobby ) — the source's own 4NF example. Suppose student S1 takes DBMS and OS, and has hobbies Cricket and Music.

Step 1 — is there a multivalued dependency? For a single Stud_ID, the set of courses and the set of hobbies are independent. So Stud_ID →→ Stud_Course and Stud_ID →→ Stud_Hobby.

Step 2 — confirm the symptom. The table holds the cross product: two courses × two hobbies = four rows. Every course is paired with every hobby, which is redundancy, not information.

Step 3 — fix. Split into one relation per multi-valued fact:

StudentCourse ( Stud_ID, Stud_Course )   key (Stud_ID, Stud_Course)
StudentHobby  ( Stud_ID, Stud_Hobby )    key (Stud_ID, Stud_Hobby)

Step 4 — verify. Each relation is in BCNF (the whole key determines the non-key attribute), and neither contains a multivalued dependency, so both are in 4NF. The two relations together carry exactly the same information as the original, with the cross-product rows removed.

Problem 4 — test a decomposition for losslessness

Relation. R ( A, B, C, D ) with dependencies A → B and C → D, key ( A, C ).

Question. Is the decomposition into R1 ( A, B ) and R2 ( A, C, D ) lossless?

Test. R1 ∩ R2 = { A }. Is A a super key of R1? Yes — A → B and R1 = { A, B }. So the decomposition is lossless.

Question. Is the alternative decomposition into R1 ( A, B ) and R2 ( C, D ) lossless?

Test. R1 ∩ R2 = ∅. The empty set is a super key of neither relation (it determines nothing). So this decomposition is lossy — joining the pieces would produce the full cross product A × B × C × D, which contains spurious tuples. The key ( A, C ) would be lost entirely.

The method to reuse in an examination
  1. Write down the functional dependencies. Nothing else is possible without them.
  2. Find the candidate key by computing closures.
  3. Test 2NF: does any non-prime attribute depend on part of a composite key?
  4. Test 3NF: does any non-prime attribute depend on another non-prime attribute?
  5. Test BCNF: is any determinant not a super key?
  6. Test 4NF: are two independent multi-valued facts in one table?
  7. Verify losslessness at the end using the R1 ∩ R2 super-key test.

3. Functional Dependencies: Meaning and Notation

Part 2  •  the single idea that makes normalization possible

Normalization is not a set of arbitrary rules. It is a set of tests applied to functional dependencies. If you cannot see the dependencies hiding in a table, you cannot normalize it — you can only memorise the steps. This chapter builds the ability to see them.

3.1 What a Functional Dependency Says

Definition

A functional dependency (FD) is a constraint between two sets of attributes of a relation. If X and Y are sets of attributes of relation R, then X → Y (“X determines Y”, or “Y is functionally dependent on X”) means that any two tuples that agree on X must also agree on Y.

Formally, as the source states it: for any two tuples t1 and t2 in R, if t1[X] = t2[X] then t1[Y] = t2[Y].

Read that sentence slowly, because it is the whole subject. The arrow does not mean “causes”, it does not mean “is calculated from”, and it does not mean “appears to the left”. It means: in every legal state of this relation, the same X value cannot be paired with two different Y values.

The source's own example is the smallest possible one. Consider a Department relation with attributes DeptId and DeptName, where DeptId is the primary key:

Table 3.1 — The source's Department relation.
DeptIdDeptName
001Finance
002Marketing
003HR

Because DeptId uniquely identifies the department, it also uniquely determines the department name. The dependency is

DeptId → DeptName

The source phrases the justification memorably: if you want to know the department name, then at first you need to have the DeptId. That “you must know X first” test is a reliable practical way to spot a dependency in a table.

From the source — a wording slip

The source then writes “DeptId is functionally dependent on DeptName” and still labels the dependency DeptId → DeptName. The sentence is backwards: in DeptId → DeptName it is DeptName that is functionally dependent on DeptId, not the other way round. The notation in the source is correct and is the one used throughout these notes; only that one explanatory sentence is inverted.

3.3 Reading a Dependency Correctly

Common mistake

Reading the arrow as a causal or computational relation. A dependency is a constraint on allowed data. The table below shows sentences people write, and which of them are correct.

Table 3.3 — Correct and incorrect readings of X → Y.
SentenceVerdictWhy
“X determines Y.”CorrectStandard reading of the arrow.
“Y is functionally dependent on X.”CorrectStandard reading of the arrow.
“X depends on Y.”WrongReverses the direction. X is the determinant.
“Y causes X.”WrongThe arrow is a data constraint, not causation.
“X is computed from Y.”WrongComputation is irrelevant to the constraint.

3.4 Finding Dependencies in a Table

Given only a table of rows, a dependency can be disproved but never proved — the rows you can see are a sample of all legal states. The practical procedure is to look for two rows with the same X and different Y; if they exist, X → Y is false.

Worked step — disproving a dependency

Take the source's Book relation (used again in Section 5.1):

BookAuthorAuthor_age
Game of ThronesGeorge R. R. Martin66
Harry PotterJ. K. Rowling49
Dying of the LightGeorge R. R. Martin66

Claim: Author → Book. Test: look for two rows with the same Author and different Book. Rows 1 and 3 both have author “George R. R. Martin” but different books. The claim is false. This is exactly the step that makes Book → Author_age a transitive dependency later in Section 5.1, and transitive dependencies are what 3NF removes.

3.5 Trivial, Non-Trivial and Completely Non-Trivial

The source gives three forms of functional dependency. The distinction looks pedantic until you write an exam answer about BCNF, where the words “trivial” and “non-trivial” decide whether a dependency violates the form.

Definitions — the three forms

Trivial: for A → B, B is a subset of A. The dependency tells you nothing new.

Non-trivial: for A → B, B is not a subset of A.

Completely non-trivial: for A → B, A ∩ B is empty (the two sides share no attribute at all).

Source examples, checked

Table 3.4 — The source's examples for each form.
FormExampleWhy it has that form
Trivial{ DeptId, DeptName } → DeptIdThe right side DeptId is a subset of the left side, so it is trivially satisfied.
Non-trivialDeptId → DeptNameDeptName is not a subset of DeptId, so the dependency genuinely constrains the data.
Completely non-trivialDeptId → DeptNameThe same dependency also has empty intersection between its sides, so it is completely non-trivial as well.
Explanation — the nesting to remember

The three classes are nested, not separate categories. The example DeptId → DeptName is simultaneously non-trivial and completely non-trivial, because its two sides share no attribute. A dependency such as {A, B} → {B, C} is non-trivial (C is not in the left side) but not completely non-trivial, because the left and right sides share B.

4. Armstrong's Axioms and Reasoning with Dependencies

Part 2  •  a small set of rules from which every valid dependency can be derived

A set F of functional dependencies that you write down for a schema is never the whole truth: it implies others. Armstrong's axioms are the inference rules that let you compute those implied dependencies. They were developed by William Armstrong in 1974, as the source notes.

4.1 The Three Primary Axioms

Armstrong's three axioms

Reflexivity. If Y is a subset of X, then X → Y. The source states it as “A → B, if B is a subset of A”. This is the rule that makes trivial dependencies true.

Augmentation. If X → Y, then XZ → YZ for any set of attributes Z. The source writes it as “AC → BC, if A → B”. Adding the same attributes to both sides preserves the dependency.

Transitivity. If X → Y and Y → Z, then X → Z. The source gives it as “If A → B and B → C, then A → C, i.e. a transitive relation”.

4.2 Derived Rules

Three further rules are commonly used because they shorten derivations. They are derived, not assumed: each can be proved from the three axioms.

Table 4.1 — Derived rules, all provable from reflexivity, augmentation and transitivity.
RuleStatementDerivation sketch
Union (additivity)If X → Y and X → Z, then X → YZAugment X → Y to X → XY; augment X → Z to XY → YZ; transitivity gives X → YZ.
Decomposition (projectivity)If X → YZ, then X → Y and X → ZY ⊆ YZ, so by reflexivity YZ → Y; transitivity with X → YZ gives X → Y.
PseudotransitivityIf X → Y and WY → Z, then WX → ZAugment X → Y to WX → WY; transitivity with WY → Z gives WX → Z.
Common mistake — decomposition is one-way

Decomposition works on the right side, never on the left. From A → BC you may conclude A → B and A → C. But from AB → C you may not conclude A → C or B → C. Splitting the left side is an invalid inference, and it is one of the most frequent mistakes in normalization answers.

4.3 Closure of a Set of Attributes

To decide whether a given set of attributes is a candidate key, you need to know everything it can determine. That is its closure.

Definition

The closure of a set of attributes X under a set of dependencies F, written X⁺, is the set of all attributes that can be functionally determined by X using the axioms. If X⁺ contains every attribute of the relation, then X is a super key; if X is also minimal, X is a candidate key.

Algorithm — computing X⁺

1. Start with the result set = X.
2. Scan the dependencies in F. If the left side of a dependency is already contained in the result set, add its right side to the result set.
3. Repeat step 2 until no new attribute is added.
4. The final result set is X⁺.

4.4 Worked Closure Computations

Worked step — a full closure

Relation R(A, B, C, D, E) with dependencies:

F = { A → B,  B → C,  CD → E }

Task: compute A⁺ and decide whether A is a candidate key.

PassResult setDependency usedReason
start{A}—Initialise with A
1{A, B}A → BLeft side {A} ⊆ result
2{A, B, C}B → CLeft side {B} ⊆ result
3{A, B, C}CD → ELeft side {C,D} ⊄ result (D missing)
stop{A, B, C}—No new attribute added

Result: A⁺ = {A, B, C}. Since D and E are missing, A is not a super key and therefore not a candidate key.

Worked step — finding a candidate key by closure

Same relation R(A, B, C, D, E) with F = { A → B, B → C, CD → E }.

Task: test {A, D}.

PassResult setDependency used
start{A, D}—
1{A, D, B}A → B
2{A, D, B, C}B → C
3{A, D, B, C, E}CD → E

Result: (AD)⁺ = {A, B, C, D, E} — every attribute. So {A, D} is a super key. Is it minimal? Test the proper subsets: A⁺ = {A, B, C} (missing D, E) and D⁺ = {D} (missing A, B, C, E). Neither subset determines everything, so {A, D} is a candidate key.

Correct result — the shortcut

Attributes that appear on the right side only can never be part of a candidate key. Attributes that appear on the left side (or nowhere) must be part of every candidate key. Here E appears only on the right, so E is excluded from keys; A and D appear on the left, so both must be present. Starting with {A, D} is therefore the right first guess — and the closure above confirms it.

4.5 Equivalence of Dependency Sets

Two dependency sets F and G are equivalent when every dependency in F is implied by G and every dependency in G is implied by F. Equivalence is what lets a designer replace a messy set of dependencies with a cleaner, smaller one without changing the meaning of the schema — and it is the theoretical justification for a lossless decomposition, covered in Chapter 12.

Explanation — why this is worth knowing

When you decompose a table in Part 3, the projections of the original dependencies onto the new tables form a new set G. If F and G are equivalent, the decomposition has preserved every constraint. If they are not, the decomposition has quietly lost a business rule — a fact worth stating in an exam answer.

5. Special Dependencies: Transitive, Multivalued and Join

Part 2  •  the three dependency types that drive 3NF, 4NF and 5NF

Ordinary functional dependencies are not the only constraint a table can violate. Three richer kinds of dependency each have a normal form aimed at them. Understanding them here makes Part 3 read as one connected argument rather than six unrelated definitions.

5.1 Transitive Dependency

Definition

A functional dependency is transitive when it is formed indirectly by two other dependencies. The source's precise statement: X → Z is transitive if all three of the following hold:

  • X → Y
  • Y does not → X  (so Y is not itself a determinant of X)
  • Y → Z

The source adds a useful scope note: a transitive dependency can only occur in a relation of three or more attributes, and it is the dependency that 3NF removes.

The source's Book example

Table 5.1 — The source's transitive-dependency example.
BookAuthorAuthor_age
Game of ThronesGeorge R. R. Martin66
Harry PotterJ. K. Rowling49
Dying of the LightGeorge R. R. Martin66

Check the three conditions:

  1. {Book} → {Author} — knowing the book tells you the author. ✔
  2. {Author} does not → {Book} — an author may write many books. ✔
  3. {Author} → {Author_age} — knowing the author tells you the age. ✔

Therefore, by transitivity, {Book} → {Author_age} holds: if you know the book name, you can know the author's age. That indirect dependency is a transitive dependency, and it is exactly the kind of dependency 3NF breaks.

Common mistake

Calling any two-dependency chain “transitive”. The middle condition matters. If Y → X also held, then X and Y would determine each other and the chain would simply be a pair of equivalent determinants, not a transitive dependency in the 3NF sense.

5.2 Multivalued Dependency

Definition

A multivalued dependency (MVD) occurs when the existence of one or more rows in a table implies the existence of one or more other rows in the same table. If a table has attributes P, Q and R, and Q and R are two independent multivalued facts about P, we write P →→ Q and P →→ R.

The source states the three conditions for a table to have a multivalued dependency, and they are worth listing exactly as given:

  1. For a dependency A → B, if for a single value of A multiple values of B exist, then the table may have a multivalued dependency.
  2. The table must have at least three columns for a multivalued dependency to exist.
  3. For a relation R(A, B, C), if there is a multivalued dependency between A and B, then B and C must be independent of each other.

The source's Student example

Table 5.2 — The source's multivalued-dependency example (as given).
StudentNameCourseDisciplineActivities
AmitMathematicsSinging
AmitMathematicsDancing
YuvrajComputersCricket
AkashLiteratureDancing
AkashLiteratureCricket
AkashLiteratureSinging

Amit takes Mathematics and has two activities; Akash takes Literature and has three. The courses and the activities are two independent lists about the same student — a course choice does not depend on an activity choice. So StudentName →→ CourseDiscipline and StudentName →→ Activities both hold. This relation violates 4NF, and the fix (decomposing into StudentCourse and StudentActivities) is worked in Section 10.3.

From the source — a repeated-row defect

In the source's corrected tables, the row “Amit / Mathematics” is listed twice in StudentCourse, and “Akash / Literature” appears three times. In a true relation the rows of a table form a set, so duplicate tuples cannot exist: the correct decomposition is StudentCourse = { (Amit, Mathematics), (Yuvraj, Computers), (Akash, Literature) } and StudentActivities = { (Amit, Singing), (Amit, Dancing), (Yuvraj, Cricket), (Akash, Dancing), (Akash, Cricket), (Akash, Singing) }. The duplicates in the source appear to be a display artefact of the slide. The corrected version is used in Chapter 10.

5.3 Join Dependency

Definition

A table is in join dependency if it can be recreated by joining multiple tables, each of which holds a subset of its attributes. A join dependency is a generalisation of a multivalued dependency, and it is the dependency that 5NF addresses: a relation is in 5NF only if it is already in 4NF and cannot be decomposed further without losing information.

The source's Employee example

Table 5.3 — The source's join-dependency example.
EmpNameEmpSkillsEmpJob (Assigned Work)
TomNetworkingEJ001
HarryWeb DevelopmentEJ002
KatieProgrammingEJ002

The source shows that this table can be decomposed into three tables — EmployeeSkills (EmpName, EmpSkills), EmployeeJob (EmpName, EmpJob) and JobSkills (EmpSkills, EmpJob) — and that joining those three reproduces the original table. The join dependency is

{ (EmpName, EmpSkills), (EmpName, EmpJob), (EmpSkills, EmpJob) }

From the source — an important qualification

The source says of this three-table decomposition “therefore it is not in 5NF”. Taken literally that is too strong: the three-table decomposition of this particular data happens to join back losslessly, but a table is only genuinely in violation of 5NF when the join dependency is not implied by the candidate keys — that is, when the constraint is a real business rule of the schema, not an accident of the rows shown. The source itself makes exactly this point in its 5NF chapter, where it distinguishes the version of the table that obeyed the tuple-formation rule (which was in 5NF) from the version that did not (which was not). These notes present the source's example as an illustration of what a join dependency is, and explain the key-implied test properly in Section 11.1.

5.4 Dependency Types and the Normal Forms They Drive

Chapter summary

Summary — Part 2
  • X → Y means equal X forces equal Y, in every legal state. X is the determinant, Y is the dependent set.
  • Trivial: B ⊆ A. Non-trivial: B ⊄ A. Completely non-trivial: A ∩ B = ∅.
  • Armstrong's three axioms are reflexivity, augmentation and transitivity; union, decomposition and pseudotransitivity are derived from them.
  • Closure X⁺ is computed by repeatedly adding right sides whose left sides are already contained; if X⁺ is everything and X is minimal, X is a candidate key.
  • A transitive dependency is a chain X → Y → Z where Y ⇏ X. It is removed by 3NF.
  • A multivalued dependency P →→ Q exists when two independent multi-valued facts sit in one table. It is removed by 4NF.
  • A join dependency exists when a table can be losslessly reconstructed from projections. It is removed by 5NF when it is not implied by the candidate keys.

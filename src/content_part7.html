29. SQL Views: Concept and Creation

Part 7  •  a stored query that behaves like a table

A view is the database's answer to a common problem: many different users need to see different slices of the same data, but you do not want to maintain a separate copy for each. A view stores the question, not the answer — and every time it is used, the question is asked again against the current data.

29.1 Definition and Base Tables

Definition (source)

An SQL View is a specific representation of data from one or more tables. The tables referred to in the view are known as base tables. Creating a view does not take any storage space, because only the query is stored in the data dictionary and the actual data is not stored anywhere.

The maximum number of columns that can be defined in a SQL View is 1000, as in tables.

The source also gives the informal framing that is worth holding alongside the formal one: views in SQL are kind of virtual tables. A view also has rows and columns as they are in a real table in the database. We can create a view by selecting fields from one or more tables present in the database. A view can either have all the rows of a table or specific rows based on a certain condition.

Explanation — why “no storage space” is a real benefit

Because only the query is stored, a view cannot become inconsistent with its base tables. There is no second copy to fall out of date — the source's phrase is that the actual data “is not stored anywhere”. This is the opposite of the redundancy problem of Part 3: a view is a form of reuse that adds no redundancy at all.

29.2 Benefits of Views

Benefits (source)

The reasons for using views in applications can be many, like:

  • Reducing complexity.
  • Improving security.
  • Renaming the table columns.

Chapter 30 expands these three into the source's fuller list of six uses (Section 30.7). The three here are the headline benefits; the six there are the detailed justifications.

29.4 Creating a View from a Single Table

Syntax (source) 
CREATE VIEW view_name AS
SELECT column1, column2.....
FROM   table_name
WHERE  condition;
PartMeaning (source)
view_nameName for the view
table_nameName of the table
conditionCondition to select rows
Example 1 — DetailsView (source)

Problem: create a view named DetailsView from the table StudentDetails, showing only the name and address of students whose id is less than 5.

CREATE VIEW DetailsView AS
SELECT NAME, ADDRESS
FROM   StudentDetails
WHERE  S_ID < 5;

Line by line: CREATE VIEW DetailsView AS names the view and begins its definition; SELECT NAME, ADDRESS chooses two columns, so the view has exactly two columns; FROM StudentDetails names the single base table; WHERE S_ID < 5 restricts the view to rows 1 to 4.

Resulting view:

Table 29.3 — The view DetailsView after creation.

kaushikKota
ChaitaliMumbai

Note what the view does not contain: the S_ID column, the AGE column, and the rows for Hardik and Komal. A view can hide both columns and rows, which is the basis of its security benefit.

Example 2 — StudentNames (source)

Problem: create a view named StudentNames showing student id and name, ordered by name.

CREATE VIEW StudentNames AS
SELECT S_ID, NAME
FROM   StudentDetails
ORDER BY NAME;

Important — ORDER BY makes this view non-updatable

This view contains an ORDER BY clause. Section 30.3 lists that as one of the conditions that prevents a view from being updated. So StudentNames can be queried but not modified through. This example is therefore a good illustration of the trade-off: ordering in a view costs updatability.

29.5 Creating a View from Multiple Tables

The source's instruction

To create a View from multiple tables we can simply include multiple tables in the SELECT statement.

Example 3 — MarksView (source)

Problem: create a view named MarksView from the two tables StudentDetails and StudentMarks, showing each student's name, address and marks.

CREATE VIEW MarksView AS
SELECT StudentDetails.NAME, StudentDetails.ADDRESS, StudentMarks.MARKS
FROM   StudentDetails, StudentMarks
WHERE  StudentDetails.NAME = StudentMarks.NAME;

Line by line: the SELECT list qualifies each column with its table, which is required here because NAME exists in both tables. The FROM clause lists both tables, producing a Cartesian product; the WHERE clause then keeps only those pairs whose NAME matches, which is precisely an equi-join. The result is one row per student who appears in both tables.

Resulting view:

Table 29.5 — The view MarksView, joining StudentDetails and StudentMarks on NAME.

29.6 Querying a View

The source's instruction

To see the data in the View, we can query the view in the same manner as we query a table:

SELECT * FROM DetailsView;
SELECT * FROM StudentNames;
SELECT * FROM MarksView;

This is the point of a view, and it is easy to overlook: once created, a view is queried exactly like a table. The user writes an ordinary SELECT and never needs to know whether the name refers to a base table or a view. In the case of MarksView, that single SELECT * hides a two-table join.

Chapter summary

Summary — Chapter 29
  • A view is a specific representation of data from one or more tables; the tables it refers to are its base tables.
  • Creating a view takes no storage space — only the query is stored, in the data dictionary. The maximum number of columns in a view is 1000.
  • Benefits: reducing complexity, improving security, and renaming columns.
  • CREATE VIEW name AS SELECT … FROM … WHERE …; creates a view from one table; including several tables in the FROM clause creates a view from multiple tables.
  • A view is queried exactly like a table, with an ordinary SELECT.

30. Modifying, Dropping and Updating Views

Part 7  •  what a view allows you to change, and what it forbids

So far a view has been read-only. This chapter covers the rest of its life: removing it, redefining it, and — most importantly for examinations — the exact conditions under which a view can be written through.

30.1 Dropping a View

Syntax (source)

We have learned about creating a View, but what if a created View is not needed any more? SQL allows us to delete an existing View. We can delete or drop a View using the DROP statement.

DROP VIEW view_name;
PartMeaning (source)
view_nameName of the View which we want to delete
Example (source) 
DROP VIEW MarksView;

What this does: it removes the view definition from the data dictionary. It does not delete any data, because the view never held any data of its own — the rows it displayed came from StudentDetails and StudentMarks, and both tables are untouched. This is an important distinction to state in an answer: dropping a view destroys a query, not data.

30.2 Creating or Replacing a View

Syntax (source)

We can use the CREATE OR REPLACE VIEW statement to add or remove fields from a view.

CREATE OR REPLACE VIEW view_name AS
SELECT column1, column2,..
FROM   table_name
WHERE  condition;
Example — adding a field to MarksView (source)

Problem: update the view MarksView and add the field AGE from the StudentMarks table.

CREATE OR REPLACE VIEW MarksView AS
SELECT StudentDetails.NAME, StudentDetails.ADDRESS, StudentMarks.MARKS,
       StudentMarks.AGE
FROM   StudentDetails, StudentMarks
WHERE  StudentDetails.NAME = StudentMarks.NAME;

Result: the view now has four columns instead of three. Fetching all the data from MarksView gives the earlier three columns plus the age:

Table 30.1 — MarksView after the CREATE OR REPLACE, with AGE added.
NAMEADDRESSMARKSAGE
RameshAhmedabad9032
KhilanDelhi8525
kaushikKota7023
ChaitaliMumbai8025
HardikBhopal7527

Why CREATE OR REPLACE rather than DROP then CREATE

Both approaches achieve the same end, but CREATE OR REPLACE is preferable in practice. Dropping a view and recreating it creates a window in which the view does not exist, and it also discards any privileges granted on the view, which must then be granted again. CREATE OR REPLACE changes the definition in one step.

30.3 Conditions Required to Update a View

This is the most examinable part of the chapter, and the source states it as a numbered list of five conditions. The framing is important: there are certain conditions needed to be satisfied to update a view. If any one of these conditions is not met, then we will not be allowed to update the view.

The five conditions (source, verbatim intent)
  1. The SELECT statement which is used to create the view should not include a GROUP BY clause or an ORDER BY clause.
  2. The SELECT statement should not have the DISTINCT keyword.
  3. The View should have all NOT NULL values.
  4. The view should not be created using nested queries or complex queries.
  5. The view should be created from a single table. If the view is created using multiple tables, we will not be allowed to update the view.
Explanation — a good way to remember the five

Notice that the five conditions all answer the same question: can the DBMS work out which base-table row this view row came from? GROUP BY and DISTINCT collapse several base rows into one, so the answer is no. A join mixes two tables, so there is no single row. A nested or complex query hides the mapping behind intermediate steps. And an ORDER BY says nothing about identity at all. If you remember the one question, you can reconstruct the five conditions in an examination.

30.4 Inserting a Row Through a View

Syntax (source)

We can insert a row in a View in the same way as we do in a table. We can use the INSERT INTO statement of SQL to insert a row in a View.

INSERT INTO view_name(column1, column2, column3,..)
VALUES(value1, value2, value3..);
PartMeaning (source)
view_nameName of the View
Example — inserting into DetailsView (source)

Problem: insert a new row into DetailsView, the view created earlier from a single table.

INSERT INTO DetailsView(NAME, ADDRESS)
VALUES("Suresh","Gurgaon");

What happens: DetailsView is a single-table view with no GROUP BY, no ORDER BY and no DISTINCT, so it is updatable — and the INSERT is therefore redirected to the base table StudentDetails. A new row is added there with NAME = 'Suresh' and ADDRESS = 'Gurgaon'.

Result: querying the view again now shows five rows:

Table 30.2 — DetailsView after the INSERT.
NAMEADDRESS
RameshAhmedabad
KhilanDelhi
kaushikKota
ChaitaliMumbai
SureshGurgaon
Note the column list — and why it matters here

The INSERT names only (NAME, ADDRESS). The base table StudentDetails has further columns (S_ID, AGE) which are not in the view, so they receive their default or NULL values in the new base-table row. That is why the view shows Suresh but cannot show an id or age for him: those columns are not part of the view at all. This is worth stating in an answer, because it shows that a view restricts what can be supplied as well as what can be seen.

30.5 Deleting a Row Through a View

Syntax and the key fact (source)

Deleting rows from a view is also as simple as deleting rows from a table. We can use the DELETE statement of SQL to delete rows from a view. Also, deleting a row from a view first deletes the row from the actual table, and the change is then reflected in the view.

DELETE FROM view_name
WHERE condition;
PartMeaning (source)
view_nameName of view from where we want to delete rows
conditionCondition to select rows
Example — deleting the row just inserted (source)

Problem: delete the last row from DetailsView — the one just added.

DELETE FROM DetailsView
WHERE NAME = "Suresh";

What happens: the DELETE is redirected to the base table StudentDetails, where the row with NAME = 'Suresh' is removed. The view then reflects the change, because it re-runs its query each time it is used.

Result: querying DetailsView again shows the original four rows, and Suresh is gone.

Table 30.3 — DetailsView after the DELETE — back to four rows.

30.6 WITH CHECK OPTION

Definition (source)

The WITH CHECK OPTION clause in SQL is a very useful clause for views. It is applicable to an updatable view. If the view is not updatable, then there is no meaning in including this clause in the CREATE VIEW statement.

  • The WITH CHECK OPTION clause is used to prevent the insertion of rows in the view where the condition in the WHERE clause in the CREATE VIEW statement is not satisfied.
  • If we have used the WITH CHECK OPTION clause in the CREATE VIEW statement, and if the UPDATE or INSERT clause does not satisfy the conditions, then they will return an error.

This is a genuinely useful mechanism, and its purpose is easy to state. A view's WHERE clause defines which rows belong to the view. Without WITH CHECK OPTION, you can insert a row through the view that does not satisfy that condition — and the row then vanishes from the view the moment it is inserted, because the view's query excludes it. WITH CHECK OPTION forbids that, turning a silent disappearance into an explicit error.

Example — SampleView with WITH CHECK OPTION (source)

Problem: create a view of students whose NAME is not null, and prevent any insert that would violate that condition.

CREATE VIEW SampleView AS
SELECT S_ID, NAME
FROM   StudentDetails
WHERE  NAME IS NOT NULL
WITH CHECK OPTION;

What the view does: it selects only S_ID and NAME, and only for rows where NAME is not null. The WITH CHECK OPTION means that any INSERT or UPDATE through this view must also satisfy NAME IS NOT NULL, or the statement fails.

The statement the source shows as invalid:

INSERT INTO SampleView(S_ID)
VALUES(6);

Why it fails: this INSERT supplies only S_ID. It does not supply a NAME, and the source's note explains the consequence: the default value of the NAME column is null. So the new row would have NAME = NULL, which violates the view's WHERE NAME IS NOT NULL condition. Because the view was created WITH CHECK OPTION, the DBMS refuses the insert and returns an error.

The key point to state in an exam

The view is updatable — the source says so explicitly: “though the View is updatable but then also the below query for this View is not valid”. The reason the insert fails is not that the view is read-only, but that the new row would fall outside the view's own condition. WITH CHECK OPTION converts that situation from a silent anomaly into a refused statement.

30.7 Uses of a View

The source closes the chapter with six reasons a good database should contain views. This is a standard examination question, and the source's own wording is worth reproducing closely.

Table 30.4 — The six uses of a view (source).
#UseThe source's explanation
1Restricting data accessViews provide an additional level of table security by restricting access to a predetermined set of rows and columns of a table.
2Hiding data complexityA view can hide the complexity that exists in a multiple-table join.
3Simplifying commands for the userViews allow the user to select information from multiple tables without requiring the user to actually know how to perform a join.
4Storing complex queriesViews can be used to store complex queries.
5Renaming columnsViews can also be used to rename the columns without affecting the base tables, provided the number of columns in the view matches the number of columns specified in the SELECT statement. Thus renaming helps to hide the names of the columns of the base tables.
6Multiple view facilityDifferent views can be created on the same table for different users.
Explanation — the six uses fall into three groups

It helps to see the pattern. Uses 1 and 5 are about security and hiding: restrict which rows and columns a user can reach, and obscure the underlying column names. Uses 2, 3 and 4 are about simplification: put the join inside the view so the user never writes it. Use 6 is about customisation: one table, many audiences, each with their own view. If you can reproduce those three headings, the six individual uses follow naturally.

Summary — Chapter 30

  • A view is updatable only if all five conditions hold: no GROUP BY or ORDER BY; no DISTINCT; all NOT NULL values; not created from nested or complex queries; and created from a single table.
  • INSERT INTO view … and DELETE FROM view … are redirected to the base table, and the change is reflected in the view.
  • WITH CHECK OPTION prevents an insert or update through the view that would not satisfy the view's WHERE condition; such a statement returns an error.
  • Six uses: restricting data access, hiding data complexity, simplifying commands, storing complex queries, renaming columns, and the multiple-view facility.
